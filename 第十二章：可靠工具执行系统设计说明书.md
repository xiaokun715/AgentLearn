# Agent Tool Execution Platform Demo

## —— 基于 LangGraph 的可靠工具执行系统

## 1. 项目概述

### 1.1 项目目标

设计并实现一个面向 Agent 的可靠 Tool Execution Platform，解决 Agent 在调用外部工具时的：

* 同步 / 异步执行
* 长耗时任务调度
* Tool 幂等
* 分布式锁
* 租约（Lease）
* 心跳（Heartbeat）
* Checkpoint
* Agent 崩溃恢复
* Tool 参数自愈
* 权限控制
* 参数注入防护
* 沙箱执行
* 超时控制
* 重复执行检测
* DAG 循环检测
* 错误分类与恢复
* 大结果处理
* Human-in-the-loop

等问题。

核心目标：

> **Agent 只负责决定“调用什么 Tool”，Tool Execution Platform 负责保证“这个 Tool 安全、可靠、可恢复地执行”。**

# 2. 核心设计原则

整个系统遵循：

```text
Agent
  │
  │ ToolCall
  ▼
Tool Gateway
  │
  ├── 参数校正
  ├── 权限校验
  ├── 注入检测
  ├── 幂等检查
  ├── 重复检测
  ├── DAG 检测
  │
  ▼
Tool Scheduler
  │
  ├── Sync Executor
  └── Async Executor
          │
          ▼
      Sandbox
          │
          ▼
      Tool Process
          │
          ▼
      Result Store
```

最重要的职责边界：

| 模块                  | 负责什么                                     |
| ------------------- | ---------------------------------------- |
| Agent               | 决策调用哪个 Tool                              |
| LangGraph           | Agent Workflow、State、Checkpoint、Recovery |
| Tool Gateway        | Tool Call 入口、安全检查                        |
| Tool Scheduler      | 同步/异步调度                                  |
| Idempotency Manager | 防止重复执行                                   |
| Lease Manager       | 租约、心跳、故障接管                               |
| Sandbox             | 资源隔离                                     |
| Tool Executor       | 真正执行 Tool                                |
| Result Store        | 保存执行结果                                   |
| Recovery Manager    | 错误恢复                                     |
| Human Manager       | 人工审批/介入                                  |

# 5. Tool Metadata

```python
class ToolMetadata(BaseModel):

    version: str
```

```python
    risk_level="medium",
    required_permissions=[
        "test.execute"
    ]
)
```

# 7. Idempotency Key

这是整个系统最重要的设计之一。

原则：

> **同一个逻辑 Tool Operation 必须具有稳定的 Idempotency Key。**

例如：

```text
idempotency_key =
hash(
    tenant_id
    + agent_id
    + tool_name
    + normalized_arguments
    + business_operation_id
)
```

不能直接：

```text
hash(arguments)
```

因为两个不同任务可能恰好参数一样。

推荐：

```text
tenant_id
+
workflow_run_id
+
logical_step_id
+
tool_name
+
normalized_arguments
```

例如：

```text
tenantA:
run_1001:
step_3:
run_test:
TC001
```

最终：

```text
idem_xxxxx
```

```text
      ▼
```

```text
      │
      ▼

      ▼

      │
```

# 10. Redis Lua 原子创建

可以使用：

```text
SET key value NX EX
```

例如：

```python
ok = await redis.set(
    key,
    processing_data,
    nx=True,
    ex=ttl

```

成功：

```text

```

说明当前请求获得执行权。

失败：

```text
ok = False
```

# 11. Case 2：Idempotency Key = PROCESSING

说明：

```text
另一个 Worker 正在执行
```

不能再次执行 Tool。

策略：

```text
PROCESSING
    │
    ├── Lease 有效
    │      ↓
    │   WAIT / POLL
    │
    └── Lease 过期
           ↓
      判断 Worker 是否死亡
           ↓
        Recovery
```

---

# 12. Case 3：Idempotency Key = SUCCESS

直接返回：

```text
cached result
```

绝对不能再次执行。

```text
Agent
 ↓
ToolCall
 ↓
Redis
 ↓
SUCCESS
 ↓
Result Store
 ↓
Return
```

---

# 13. Case 4：Idempotency Key = FAILED

需要区分：

```text
retryable
non_retryable
```

例如：

```text
网络超时
    → retry

服务 503
    → retry

参数错误
    → parameter repair

权限不足
    → 不 retry

Tool 不存在
    → 不 retry

业务逻辑失败
    → 根据 Tool Policy 决定
```

所以 `FAILED` 不能简单理解成：

```text
FAILED → retry
```

而应该：

```text
FAILED
  │
  ▼
ErrorClassifier
  │
  ├── RETRY
  ├── REPAIR
  ├── FALLBACK
  ├── HUMAN
  └── ABORT
```

# 15. Heartbeat

Worker 执行期间：

```text
Tool Process
     │
     ├── heartbeat
     ├── heartbeat
     ├── heartbeat
     └── heartbeat
```

例如：

```text
Lease TTL = 30s

Heartbeat = 10s
```

Worker 每 10 秒：

```text
EXPIRE lease:{call_id} 30
```

但生产实现必须保证：

> 只有当前 `lease_id` 持有者才能续租。

否则 Worker A 已经失效：

```text
Worker A
```

Worker B 接管：

```text
Worker B
```

此时 A 恢复后不能继续续租。

因此需要：

```text
lease_id compare-and-renew
```

使用 Lua 保证原子性。

# 16. Agent 心跳

这里需要区分两个 Heartbeat。

### Worker Heartbeat

证明：

```text
Tool 正在执行
```

### Agent Heartbeat

证明：

```text
Agent / Workflow 仍然活着
```

例如：

```text
Agent
  │
  ├── Tool A
  ├── Tool B
  │
  └── heartbeat
```

Agent 每隔：

```text
5~15s
```

向：

```text
agent:{agent_id}:{run_id}
```

发送 heartbeat。

---

# 17. 为什么需要 Agent Heartbeat？

因为存在：

```text
Agent
  ↓
提交 Async Tool
  ↓
Agent Crash
```

Tool 可能还在运行。

平台需要知道：

```text
Agent 是否还存在？
```

如果：

```text
Agent Lease Expired
```

可以根据 Policy：

```text
继续执行 Tool
```

或者：

```text
Cancel Tool
```

例如：

```text
non-destructive Tool
    → 继续

expensive Tool
    → cancel

dangerous Tool
    → human review
```

# 19. Agent Crash Recovery

假设：

```text
Agent

Step 1
  ↓
Step 2
  ↓
Tool Call
  ↓
CRASH
```

重启：

```text
Load Checkpoint
      │
      ▼
step = 2
      │
      ▼
pending_tool_call exists
      │
      ▼
Query Idempotency Key
```

如果：

```text
SUCCESS
```

直接拿结果。

如果：

```text
PROCESSING
```

等待。

如果：

```text
FAILED
```

进入 Recovery。

如果：

```text
NOT FOUND
```

说明可能之前根本没有成功提交 Tool。

这时可以重新提交。

---

# 20. 为什么 Checkpoint + Idempotency 必须一起使用？

这是面试中的一个重点。

单独 Checkpoint：

```text
Agent Crash
 ↓
Resume
 ↓
重新执行 Tool
```

可能导致：

```text
重复扣款
重复创建订单
重复执行测试
```

单独 Idempotency：

```text
Tool 不重复
```

但是 Agent：

```text
不知道自己执行到哪里
```

所以：

```text
Checkpoint
+
Idempotency
```

解决两个不同的问题：

| 机制          | 解决         |
| ----------- | ---------- |
| Checkpoint  | Agent 执行进度 |
| Idempotency | Tool 重复执行  |

# 21. 参数自愈机制

Agent/LLM 生成 Tool Call 很容易出现：

```json
{
  "timeout": "300"
}
```

但是 Tool 要求：

```python
timeout: int
```

或者：

```json
{
  "test_cases": "TC001"
}
```

Tool 要求：

```python
test_cases: list[str]
```

因此 Tool Gateway 在执行之前：

```text
Tool Call
    ↓
Schema Validation
    ↓
Parameter Repair
    ↓
Validation
    ↓
Execute
```

# 23. 参数自愈限制

不能让 LLM 随便修改参数。

例如：

```text
timeout = 300
```

不能自动变成：

```text
timeout = 300000
```

所以：

```text
LLM Repair
     │
     ▼
Schema
     │
     ▼
Business Constraints
     │
     ▼
Permission Policy
```

例如：

```python
timeout: int

constraints:
1 <= timeout <= 600
```

最终：

```text
LLM Repair
+
Deterministic Validator
```

而不是：

```text
LLM Repair Only
```

# 26. Permission Check

```text

       │

       │
```


# 29. 超时机制

至少设置三层：

```text
Tool Timeout
    ↓
Sandbox Timeout
    ↓
Worker Lease Timeout
```

例如：

```text
Tool timeout = 300s

Sandbox timeout = 310s

Lease = 330s
```

原因：

不能：

```text
Tool 300s
Lease 30s
```

否则 Tool 还在运行，Lease 已过期。

# 35. Recovery Policy

建立：

```text
Error
 ↓
Classifier
 ↓
Recovery Policy
```

例如：

| Error              | 策略                       |
| ------------------ | ------------------------ |
| 参数错误               | 参数修复                     |
| 权限错误               | Stop                     |
| Timeout            | Retry / Increase timeout |
| Network Error      | Retry + Backoff          |
| 429                | Backoff                  |
| 503                | Retry                    |
| Resource Exhausted | 降低资源/换节点                 |
| Tool Not Found     | Fallback                 |
| Sandbox Error      | 新建 Sandbox               |
| Business Error     | 根据业务规则                   |
| 高风险错误              | Human                    |

# 36. Retry Policy

采用：

```text
Exponential Backoff
+
Jitter
```

例如：

```text
1s
2s
4s
8s
```

加：

```text
random jitter
```

避免：

```text
大量 Agent
    ↓
同时 Retry
    ↓
服务雪崩
```

```python
async def tool_node(state):
```

# 56. Worker Crash 恢复

另外一个场景：

```text
Worker A
   │
   ▼
Tool Execute
   │
   X
Worker Crash
```

Lease：

```text

```

Reaper：

```text
Lease Reaper
     │
     ▼
Detect Expired
     │
     ▼
Check Process
     │
     ▼
Acquire Recovery Lock
     │
     ▼
New Worker
```

但这里仍然需要：

```text
Idempotency
```

避免 Worker A 实际上没有死，只是网络断开：

```text
Worker A
      │
      ├── actually running
      │
Worker B
      │
      └── starts same Tool
```

因此对于**不可真正幂等的副作用 Tool**，不能简单依靠 lease 过期就重执行。

应该：

```text
lease expired
+
execution state uncertain
```

进入：

```text
RECOVERY_REQUIRED
```

高风险操作：

```text
Human
```

```text

IDEMPOTENT
```

这个设计可以明显提高 Demo 的工程深度。

# 75. 最终面试总结

如果面试官问：

> **“你怎么设计一个 Agent Tool Execution System？”**

可以回答：

> 我会把 Tool 调用从 Agent Workflow 中抽离出来，设计独立的 Tool Execution Platform。Agent 通过 Tool Gateway 提交标准化 ToolCall，Gateway 首先进行 Schema 校验、参数自愈、权限检查和参数注入防护，然后基于 Tool 的执行时间和执行模型选择同步或者异步 Executor。
>
> 对每个 ToolCall，我会生成稳定的 Idempotency Key。请求首先查询 Redis，如果不存在则通过 `SET NX` 或分布式锁竞争执行权，并将状态原子设置为 PROCESSING；如果已经存在，则根据 SUCCESS、PROCESSING、FAILED 分别进行结果复用、等待/检查 Lease、或者按照错误恢复策略处理。
>
> 长任务由 Worker 执行，并通过 Lease + Heartbeat 防止 Worker 异常导致任务永久卡住。Agent 自身也维护 Heartbeat，用于判断 Agent/Workflow 生命周期。
>
> Tool 执行前会进行参数 Schema 校验和有限的 LLM 参数修复，同时经过确定性的业务约束和权限校验。真正执行发生在 Sandbox 中，限制 CPU、Memory、Disk、Network 和 Timeout。
>
> Agent 使用 LangGraph Checkpoint 保存每一步执行状态。如果 Agent 崩溃，恢复后读取 Checkpoint，发现存在 Pending Tool Call，就通过 Idempotency Key 查询 Tool 状态，从而避免重复执行。
>
> Tool 返回结果后，根据结果大小决定直接放入 Agent Context，还是保存到 Object Storage，只向 Agent 返回 artifact_id 和 preview。
>
> 最后，我还会增加错误分类、指数退避重试、Fallback、重复 Tool 检测、DAG Cycle Detection 和 Human-in-the-loop。对于真正的非幂等外部副作用，不能仅靠 Redis Lock 保证 exactly-once，而应该结合业务幂等键、状态查询或者人工确认。

**一句话概括：**

> **LangGraph 保证 Agent Workflow 的状态和恢复；Tool Execution Platform 保证 Tool Call 的可靠执行；Idempotency 保证不重复产生副作用；Lease 保证任务可接管；Sandbox 保证执行安全；Checkpoint 保证 Agent 崩溃后可以继续；Recovery Engine 保证异常情况下系统不会简单地无限 Retry。**

## 1. 遇到的最大困难是什么？如何解决？

```commandline
我在 AI4Test 项目中遇到的最大挑战，是如何把测试人员依赖领域经验完成的工作，转化成 Agent 能够理解、执行和验证的任务流程。

因为我本身不是传统的测试业务人员，刚开始对一些具体测试场景的理解不够深入。例如，拿到一个测试需求后，应该关注哪些测试点、具体执行哪些步骤、出现异常后应该先检查什么，以及如何逐步缩小范围定位根因。这些内容并不是简单调用大模型或者检索几份文档就能解决的。
针对这个问题，我主要从三个方面推进。

第一，主动补齐业务知识。我不会只根据自己的理解设计 Agent，而是结合实际需求和测试文档梳理业务流程，并与熟悉相关测试场景的同事沟通。对于不清楚的地方，我会把问题具体化，例如需求对应哪些测试点、每个测试点需要什么前置条件、执行结果如何判断，以及失败后通常会检查哪些指标和日志，再针对这些问题向业务同事请教。

第二，把业务经验沉淀成系统能力。对于沟通得到的业务规则和处理经验，我会进一步整理成结构化的任务步骤、输入输出约束、工具调用要求和结果校验规则，融入相应的 Agent 或 Skill 中。这样就不是每次都依赖模型临时推理，而是让 Agent 在明确的业务边界内完成任务。

第三，建立反馈和迭代机制。Agent 的结果不能只看回答是否合理，还要看测试步骤是否可执行、关键测试点是否遗漏、工具调用是否正确，以及故障分析有没有证据支撑。如果发现结果不符合预期，我会结合执行记录和业务同事的反馈分析问题究竟来自业务理解、知识检索、任务规划还是工具执行，再针对具体环节优化。

这件事让我认识到，工业场景中的 Agent 开发并不是单纯的模型应用开发。开发人员需要主动理解业务、和领域专家建立有效协作，再把专家经验沉淀为可复用、可验证的系统能力。
```

## 2. 你具体怎么拉人、怎么和测试同事沟通？

```commandline
我拉人主要分三步：先找对关键人，再降低参与成本，最后用结果建立信任。

第一，找对关键人。我不会一开始就拉一大群开会，而是先找测试负责人和一两位资深测试同事，跟他们讲清楚三件事：这个 Agent 要解决什么问题、能帮他们省什么、需要他们投入多少时间。先争取关键人的支持，再由他们帮我推荐合适的同事，比我自己挨个找人有效得多。

第二，降低参与成本。测试同事本身工作很忙，所以我尽量不让他们从零开始写。我会先把需求文档、历史用例和流程整理成一版草稿，带着具体问题去沟通，比如"这个场景的前置条件是不是 A""失败后一般先看哪几个日志"，而不是问"这个业务怎么测"这种大而空的问题。形式上尽量轻量：日常用群和文档异步确认，每周固定半小时做一次评审，有争议的点再单独拉会。

第三，形成固定的协作机制。我们约定了一个简单流程：我出 Agent 草稿，测试同事只做 review 和纠错，确认后的结论由我整理进知识库或规则里；每个阶段选一两个典型场景做试点，把节省的时间、发现的问题量化出来给大家看。这样他们能感受到自己是在"定义标准"，而不是"给开发打杂"，参与意愿会高很多。

沟通时我会注意两点：一是用他们的语言，尽量用测试用例、缺陷、复现步骤这些他们熟悉的表达；二是每次沟通结束前复述一遍我的理解，请他们确认，避免我自以为懂了。遇到同事担心 Agent 替代人工，我会明确说清楚定位是辅助和提效，关键判断仍然由测试同事把关，并且把他们的经验署名沉淀下来。
```

## 3. 测试流程不懂，怎么知道 Agent 生成的测试步骤对不对？

```commandline
我不会用"模型自己说对不对"来判断，而是用三层验证。

第一层是业务标准。我会先和测试同事把"什么样的步骤算对"定义清楚，包括前置条件是否完整、操作步骤是否可执行、预期结果是否明确、关键测试点有没有覆盖。然后把历史真实需求和缺陷整理成一套评测集，由测试同事标注出正确步骤和必须覆盖的测试点，作为回归验证的基准。没有这套标准，后面所有讨论都会变成主观争论。

第二层是可执行性。Agent 生成的步骤不能只停留在文字上，要在测试环境里真正执行，看能不能跑通、断言能不能验证、产生的日志和数据是否符合预期。对于不能自动执行的部分，我会把它拆成人工可操作的检查清单，请测试同事按清单实际走一遍。

第三层是结果可追溯。Agent 给出的每个测试点、每个判断，我都会要求能对应到具体的需求条目、文档片段或历史用例，并保留执行记录和工具调用日志。这样测试同事 review 时不是在"信或不信"，而是在核对证据。如果他们改动了某一步，我会记录修改原因，把高频问题沉淀成规则或示例，再进入下一轮评测。

衡量上我会看几个指标：步骤可执行率、关键测试点覆盖率、人工修改率，以及漏测和误报的情况。先用小范围试点、人工把关，稳定后再逐步扩大范围。
```

## 4. 出了问题，你怎么和业务同事一起找根因？

```commandline
出问题后我会按"先止损、再复现、后定位"的顺序推进，并且一定拉上业务同事一起看。

第一步是先控制影响。确认问题影响哪些场景、是否已经产生错误结果，必要时先回退到上一个稳定版本或切回人工流程，同时把现场保留下来：输入数据、Agent 的完整执行轨迹、工具调用参数和返回、使用的模型和 Prompt 版本、相关日志。

第二步是一起复现。我会把问题收敛成最小可复现的输入，约上发现问题的测试同事一起看，避免我一个人在那边猜。分工上通常是他判断业务上应该是什么结果，我负责查链路上哪一步偏了。

第三步是分层定位。我会沿着"需求理解 → 知识检索 → 任务规划 → 工具调用 → 执行环境 → 结果校验"逐层排除：是业务规则没有沉淀进去，还是检索到了错误的文档，还是规划漏了步骤，还是工具参数传错、环境本身有问题。每一层都用证据说话，而不是先入为主地认为是大模型不行。

定位清楚后，我会把结论、修复方案、责任人和时间点写进问题记录，修复后做回归，并把这次 case 补进评测集，避免同类问题再出现。沟通上我的原则是先把问题认下来、说清楚影响和临时方案，再讨论原因，不甩锅也不过度承诺。
```

## 5. 你最大的困难到底是技术问题，还是业务问题？

```commandline
如果只选一个，我认为主要矛盾是业务问题，技术是实现手段。

一开始我也以为难点在技术上，比如模型效果、工具调用稳定性。但做的过程中发现，模型能力本身往往够用，真正卡住的是业务侧：什么算测试点覆盖完整、什么算步骤正确、失败了应该先看哪里，这些标准在业务同事脑子里，是隐性的，文档里也不完整。如果这些定义不清楚，技术做得再好也只是在优化一个错误的目标。

当然技术问题也存在，比如结果不稳定、评测不好做、工具调用会出错，但这些可以通过工程手段逐步收敛：加约束、加校验、做评测集、人工兜底。而业务知识的获取、和领域专家达成共识、把经验变成可执行的规则，成本更高，也更难被替代。

所以我的判断是：业务问题是主要矛盾，技术问题是可以持续迭代的次要矛盾。这也影响了我的工作方式——我会先花时间把验收标准和业务规则问清楚，再动手做技术方案，而不是上来就调模型。这件事也让我从一个只关注技术实现的人，转变成愿意先理解业务、再用工程手段解决问题的角色。
```

## 7. 你最有成就感的一件事是什么？

## 8. 讲一次失败或受挫的经历

```commandline
有一次我负责的一个 Agent 功能，前期 demo 效果很好，但上线试点后业务同事的使用率很低。

我一开始以为是模型效果不够，后来去访谈才发现，真正的问题是它没有嵌入同事现有的工作流程：他们需要额外打开一个页面、手动复制输入，而且结果格式和他们习惯的用例模板不一致。也就是说，我优化的是自己认为重要的指标，而不是用户的实际路径。

这次之后我调整了做法：先跟使用方确认工作流和验收标准，再决定技术方案；能嵌进现有工具就不另起入口；每个版本都找真实用户试用，而不是只看离线评测。

这件事对我的影响是，我不再默认"技术效果好就等于有价值"，而是会先问清楚谁用、在什么场景用、怎么判断有用。
```

## 9. 和同事意见不一致或者发生冲突时，你怎么处理？

```commandline
我一般会先把"观点冲突"和"情绪冲突"分开处理。

如果是方案分歧，我会先回到共同目标：我们各自想解决什么问题、判断标准是什么。然后把分歧拆成具体可验证的点，比如用数据、试点结果或者小范围验证来判断，而不是靠谁声音大。如果一时验证不了，我会尊重负责人的决策，先把事情推进，同时把风险和我的保留意见记录清楚。

如果是情绪上的冲突，我会先私下沟通，避免在群里激化。先听对方把话说完，确认他真正在意的是什么，再表达我的考虑。大多数情况下，冲突背后是信息不对称或者目标不一致，把这两点对齐后就好解决了。

我的原则是对事不对人，不翻旧账，也不为了表面和气回避问题。
```

## 13. 你平时怎么学习新技术？

```commandline

第三步是总结成文档或者内部分享，把踩过的坑和适用边界记下来。我觉得能讲清楚、能被别人复用，才算真正学会。
```

## 14. 在团队里你通常扮演什么角色？

```commandline
我通常是比较偏"推进和落地"的角色。

一方面我会主动把模糊的需求拆成可执行的任务，明确输入输出和验收标准；另一方面我会关注跨角色协作，把业务、测试和开发之间的信息对齐，减少来回返工。

在技术讨论里我不一定是声音最大的那个，但比较习惯把方案的风险和边界讲清楚，也愿意承担那些需要深入排查的问题。如果团队需要，我也不排斥做文档、评测规范这类"不显眼但重要"的基础工作。
```

## 15. 如果领导安排了一件你不认同的任务，你会怎么做？

```commandline
我会先确认自己是不是掌握了完整信息。很多不认同是因为我只看到了技术侧，而领导可能掌握业务优先级或者时间窗口。

确认之后，如果仍然有不同意见，我会私下把顾虑讲清楚，重点说风险和替代方案，而不是只说"我不同意"。比如这个方案可能带来的维护成本、对现有系统的影响，以及我建议的做法。

表达完之后，如果决策还是不变，我会按决定执行，并把自己担心的风险点记录下来、提前做兜底。我认为职业性体现在：可以充分讨论，但决定之后不阳奉阴违。
```

## 16. 入职后你打算怎么快速上手？

```commandline
我会分三步走。

第一个月，重点是搞清楚业务和系统：业务目标是什么、核心流程怎么走、系统边界和关键模块在哪里，同时把代码和文档过一遍，遇到不清楚的就找对应同事确认。我会给自己列一个问题清单，尽快把认知盲区补上。

第二到第三个月，争取独立承担一个完整的模块或需求，从方案设计到上线走一遍，在做的过程中验证自己的理解，并建立和上下游同事的协作方式。

三个月之后，我希望能在负责的范围内做持续优化，比如效果评测、稳定性或者效率提升，并逐步把经验沉淀成文档。整体原则是先融入、再交付、后优化，不急于证明自己。
```

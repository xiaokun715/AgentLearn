# agent-traffic-gateway

> **高并发大流量 Agent 网关 Demo —— 把「高并发」从一句形容词变成一组可计算的数**
>
> 多级限流 ＋ 准入控制 ＋ 有界队列与公平调度 ＋ 请求合并 ＋ 分层缓存
> ＋ 并发信号量 ＋ 端到端超时预算 ＋ 重试预算 ＋ 熔断 ＋ 分级降级 ＋ 弹性伸缩

## 一句话定位

> 「我们系统能扛多少 QPS？」—— 答不上来这个数，后面所有治理手段都是拍脑袋。
>
> 本 Demo 做的第一件事是**算清楚容量**：`上游并发 / 平均服务时间`。
> 第二件事是把超出的部分用一个**体面的方式**处理掉 —— 不是「变慢」，
> 也不是「排队等到超时」，而是有判据、有原因、有分级的拒绝与降级。
> 第三件事是给出**雪崩发生前的 30 秒**该看哪个指标。

它由一台机器上的**确定性离散时间仿真器**驱动：虚拟时钟按整毫秒推进，
可以在一秒钟内跑完「5 分钟、多租户、上游会抖动、突发 8 倍」的流量，
并给出 P50/P99、吞吐、队列深度、饱和点这些真实指标。

```
                    客户端 / SDK（长连接 SSE）
                              │
                              ▼
    ┌─────────────────── 接入层 ────────────────────┐
    │  连接管理 · 全局令牌桶 · 租户配额               │
    └───────────────────────┬──────────────────────┘
                            ▼
    ┌──────────── 流量治理（本 Demo 的主角）────────────┐
    │  ① 超时预算   deadline = now + budget            │
    │  ② 边缘限流   令牌桶（保护自己）                   │
    │  ③ 租户配额   多租户隔离                          │
    │  ④ 熔断检查   上游已挂就别排队了                   │
    │  ⑤ 缓存查询   L1 → L2 → 语义                     │
    │  ⑥ 请求合并   singleflight                       │
    │  ⑦ 准入控制   预计完成时间 vs deadline            │
    │  ⑧ 排队调度   有界队列 + 优先级老化 + WFQ          │
    └───────────────────────┬──────────────────────┘
                            ▼
    ┌───────────── 并发控制（信号量）─────────────┐
    │  L = 并发上限（Little's Law 里唯一能直接控制的量）│
    │  超期清扫 · 取消传播                          │
    └───────────────────────┬──────────────────────┘
                            ▼
                上游 LLM（外部 · 有配额 · 会抖动）
                            ▼
    ┌─────────────── 观测与自适应 ────────────────┐
    │  P99 / 队列深度 / 排队压力 → 扩容 · 降级 · 熔断 │
    └──────────────────────────────────────────────┘
```

## 特性一览

| 主题 | 落地 |
|---|---|
| **容量是可计算的** | `domain/policy.py::upstream_capacity_rps`：`并发 / 服务时间`。实测吞吐被压在这个上界附近，且**过载后回落** |
| **利用率悬崖** | 排队 P50 从 1ms → 0.5s → 1s → 2s → 5s 的双曲线形状，全部由仿真跑出来，不是引用教科书 |
| **多级限流** | `gateway/limiter.py`：令牌桶（惰性补桶，无需定时器）+ 滑动窗口（顺带说明固定窗口的边界问题） |
| **准入控制** | 判据是「预计完成时间」而不是「队列长度」—— 把**时间**问题当成**空间**问题是最常见的设计错误 |
| **拒绝原因可行动** | 7 种 `RejectReason`，每种都带「对调用方意味着什么」（§7.4），分成配额类与此刻类 |
| **有界队列** | 快速失败；实测把超期数从 243 降到 27，代价是 8% 的显式拒绝 |
| **三种调度策略** | FIFO / 优先级+老化 / WFQ 虚拟时间。**只换策略、流量完全相同**，公平性差异可单独读出 |
| **请求合并** | singleflight，合并键用**精确**指纹（比缓存更严格：合并会让两个请求共享同一个响应对象） |
| **分层缓存** | L1 / L2 / 语义 + 负缓存 + **TTL 抖动**（固定 TTL 会把缓存雪崩变成周期性事件） |
| **并发信号量** | 把 Little's Law 里的 `L` 变成一个明确的数；实测在途请求被严格钉在 8 |
| **端到端超时预算** | 一个绝对 deadline，每层用剩余时间。实测：**76 次上游调用是「做完了才被丢弃」的** |
| **超期清扫** | 把超期判定从「出队那一刻」前移到「过期后 50ms」；实测吸收了 88% 的判定 |
| **重试预算** | Google SRE 式：每成功一个补 0.1 个令牌，每次重试耗 1 个 → **永不自我放大**。实测放大比 1.25 → 1.10 |
| **熔断器** | 窗口 + 最少样本数 + 冷却 + 半开探测。实测在上游 70% 故障时把超期数降到 0 |
| **分级降级** | 按**排队压力**三档丢弃 + brownout 切小模型；实测吞吐 2.73 → 7.97 RPS |
| **降级必须可见** | 每个降级响应都带 `degraded=True` —— 不标注就是静默故障 |
| **弹性伸缩** | 三种指标跑同一场景：CPU 与 QPS **一次都不触发**，队列深度触发 9 次、派发量 ×2 |
| **可观测性** | 按原因分的拒绝率、分租户分位数、**排队压力**时间线、ASCII 星图 |
| **启动自检** | 8 项：并发不得超配额、丢弃阈值必须与超时预算自洽、边缘限流要略高于容量…… |
| **热配置** | 全部阈值集中在 `GatewayConfig` + `configs/gateway.yaml`，拼错的键直接报错 |
| **零外部依赖** | 只有 `pydantic` + `pyyaml`；克隆下来就能跑 |

### §2 容量曲线（实测）

上游 8 并发 × 1.5s 平均服务时间 = **理论容量 5.33 RPS**。

| 到达率 | ρ | 完成吞吐 | P50 | P99 | 排队 P50 | 成功 |
|---|---|---|---|---|---|---|
| 1.0 | 19% | 1.00 | 1.5s | 5.0s | 1ms | 97.6% |
| 2.0 | 38% | 2.10 | 1.5s | 5.0s | 1ms | 98.8% |
| 3.0 | 56% | 2.83 | 1.5s | 5.0s | 1ms | 95.0% |
| 4.0 | 75% | 3.85 | 2.0s | 5.0s | 1ms | 92.8% |
| 4.7 | 88% | 4.42 | 2.0s | 8.0s | 500ms | 88.9% |
| 5.3 | 99% | 4.72 | 3.0s | 8.0s | 1.0s | 89.2% |
| 6.0 | **112%** | **4.92** ← 峰值 | 5.0s | 12.0s | 2.0s | 81.4% |
| 8.0 | 150% | **3.10** ← 回落 | 8.0s | 20.0s | 5.0s | 39.5% |

**注意最后两行**：到达率从 6.0 涨到 8.0（+33%），完成吞吐反而从 4.92 掉到 3.10（−37%）。
原因是超期的请求仍然占着并发槽位跑完了才被丢弃。

$$
\text{吞吐} \le \frac{\text{并发上限}}{\text{平均服务时间}} < \frac{1}{\text{平均服务时间}}
$$

### §7 准入控制四档隔离（实测，到达率 8.0 RPS = 容量的 150%）

| 配置 | 吞吐 | 成功 | P50 | P99 | 主要拒绝原因 |
|---|---|---|---|---|---|
| ① 无界队列，无准入无丢弃 | 2.78 | 35.5% | 12.0s | 20.0s | —（全部超期）|
| ② 只加有界队列 | 4.73 | 60.5% | 5.0s | 12.0s | `QUEUE_FULL` |
| ③ 只加准入控制 | 4.36 | 55.7% | 8.0s | 12.0s | `DEADLINE_INFEASIBLE` |
| ④ 有界队列 + 准入 + 分级丢弃 | **4.98** | **63.6%** | **5.0s** | **8.0s** | `OVERLOADED` |

每一档的收益都能单独读出来：超期数 243 → 44 → 65 → 20。

### §9/§10 请求合并与分层缓存（实测，热点 Zipf 流量）

| 配置 | 上游调用 | 上行占比 | 减负 | 吞吐 |
|---|---|---|---|---|
| ① 裸奔 | 421 | — | 0% | 10.32 |
| ② 只加请求合并 | 259 | 53.5% | 44% | 11.62 |
| ③ 合并 + L1/L2 | 76 | 15.7% | 84% | 12.07 |
| ④ 合并 + 分层 + 语义 | **52** | **10.7%** | **89%** | 12.07 |

④ 的 52 次上游调用里：搭车 8 次、L1 命中 329 次、语义命中 95 次。
**合并放大比 2.21×** —— 这是 Agent 网关相对普通 API 网关独有的净增量价值。

### §8.3/§8.4 公平调度（实测，whale 12 RPS + mouse 0.5 RPS）

| 策略 | whale P99 | mouse P50 | mouse P99 | mouse 成功 |
|---|---|---|---|---|
| ① FIFO | 20.0s | 12.0s | 12.0s | **4.3%** |
| ② 优先级 + 老化 | 20.0s | 12.0s | 12.0s | 4.3% |
| ③ WFQ 加权公平 | 20.0s | **2.0s** | **8.0s** | **100.0%** |

全局 P99 三行完全一样 —— 因为 whale 占了 96% 的请求，它把整体分位数拉住了。
**只有分租户看，才发现 mouse 在 FIFO 下被挤成了什么样。**

### §14.1 弹性伸缩指标（实测，上游第 10 秒变慢 3 倍）

| 扩容指标 | CPU 读数 | QPS | 队列深度 | 扩容次数 | 派发量 | 吞吐 |
|---|---|---|---|---|---|---|
| CPU | 0.67 | 1.4 | 49 | **0** | 129 | 1.40 |
| QPS | 0.67 | 1.4 | 49 | **0** | 129 | 1.40 |
| QUEUE_DEPTH | 0.67 | 1.5 | **23** | **9** | **253** | 1.52 |

上游变慢后本地容量从 5.33 掉到 1.78 RPS，队列开始堆积。
CPU 读数峰值 0.67（永远够不到 70% 的阈值）；QPS 测的是「已经服务了多少」
而不是「欠了多少」，瓶颈在自己身上时它永远显示正常。

## 关键设计取舍（这些是面试会追问的地方）

### 1. 量「容量」之前，先把缓存和降级关掉

第一版 `capacity` 场景跑出来的曲线是这样的：到达率 12 RPS，完成吞吐 11.88 RPS ——
**超过了理论容量 5.33 一倍多**。

原因有两个，都是「衡量的对象被另一个机制挡在了后面」：

* 缓存把九成请求吸收了，它们根本不碰上游；
* 过载触发了降级（切小模型），服务时间缩到 0.35 倍 —— **等于凭空把容量放大近 3 倍**。

所以本 Demo 里所有「量上游行为」的实验都必须走两个隔离辅助：

```python
upstream_bound()   # 关缓存、关合并、关降级 —— 让上游成为真瓶颈
queue_only()       # 再关丢弃、准入、清扫 —— 让「排队」这件事能被单独观察
```

`queue_only` 尤其重要：**分级丢弃在过载时非常霸道**，它会在准入之前把大部分请求
拒掉，于是队列永远建不起来。我一开始用默认配置测「调度公不公平」，
三种策略跑出来一模一样 —— 不是策略没差别，是丢弃先把差异抹平了。

**一个实验只回答一个问题。**

### 2. 丢弃阈值用「排队压力」，不是「并发利用率」

第二版用 `inflight / limit` 当阈值，结果一个**健康的**系统在稳态下会拒掉 5% 的请求。

因为有了信号量之后，「并发槽位全满」恰恰是**设计工作点**，不是过载。
一个正常运行的网关，利用率长期贴着 1.0。

改成无量纲的**排队压力**之后，阈值才变得可解释、也与部署规模无关：

```
压力 = 预计排队时间 / 单次服务时间
```

它还顺带解决了另一个问题：这个量正是 §16.3 里那个「雪崩前最有价值的信号」——
「排队已经超过计算」。同一个数，既驱动丢弃决策，又驱动告警，语义完全一致。

### 3. 一条判据在代码里成立、在行为上永远不触发

`DEADLINE_INFEASIBLE`（预计完成时间超过 deadline）实现了、单测过了，
但在整个场景里**一次都没出现**。原因是我把分级丢弃放在了它前面：

```
排队压力 ≥ 6.0  →  CRITICAL 丢弃
预计完成 > deadline  →  需要排队压力 > 5.0
```

5.0 < 6.0，所以每条注定超时的请求都先被 CRITICAL 丢弃拦下了，
调用方拿到的永远是笼统的 `OVERLOADED`。**§7.4 那条「拒绝要给出可行动的信息」
在代码里成立、在行为上失效。**

两处修正：

1. 把可行性判据**提到丢弃之前** —— 代价相同，但它是关于**这一个请求**的精确陈述；
2. 在启动自检里加一条：`shed_critical_pressure × 服务时间` 必须大于
   `预算 − 服务时间`，否则就是「有一条判据永远死着」。

第 2 条是这类 bug 的通用解法：**两个都对、但互相遮蔽的阈值，必须有人检查它们的自洽性。**

### 4. 「放大比」不能同时承载两件事

`重试放大比` 一开始算的是「上游调用数 / 请求总数」。于是缓存命中会让它**低于 1**，
看起来像「重试把负载减小了」。一个指标同时承载「重试」和「减负」两件事，
就两件事都读不出来。

拆成两个：

| 指标 | 定义 | 回答的问题 |
|---|---|---|
| 重试放大比 | 上游提交数 / 首次提交数 | 重试把负载放大了多少 |
| 上行占比 | 上游提交数 / 请求总数 | 缓存和合并减负了多少 |

还有一处更隐蔽的：一开始我从终态记录里统计「上游调用数」。但**重试复用同一个
request_id**，最终只留一条终态记录 —— 实测朴素重试发生了 67 次重试，
统计出来的放大比却是 **1.00**。这类 bug 的特点是「数字看起来完全正常」，
所以只有拿一个已知答案的场景去对照才能发现。

### 5. 压测结束时未完成的请求必须计入

第一版跑完「无治理」场景，统计出来 240 个请求里只有 187 个有结果 ——
剩下 53 个**还在队列和上游里**，也就是根本没进入任何统计。

而它们恰好是**最慢的那一批**。漏掉它们，压测结果会系统性偏乐观，
而且偏差方向与「过载程度」正相关：系统越糟，看起来越好。

修法是收尾时 `drain_pending()`：把队列里的、上游在途的、
还挂在 singleflight 上的，全部如实记为 `TIMEOUT`。

### 6. 合并最难的不是「合并」，是「不泄漏」

singleflight 最容易出的 bug 是**等待者永远挂起**：leader 走了一条没有扇出的路径
（被准入拒绝、排队超时、上游失败不重试），而搭车者还在原地等。

所以本 Demo 把所有终态收敛到**一个出口** `Gateway._finish()`：

```python
def _finish(self, req, ...):
    self._emit(req, ...)                       # 记录 leader
    key = self._leader_key.pop(req.request_id, None)
    if key:                                    # 终结所有搭车者
        for rider in self.coalescer.complete(key):
            self._emit(rider, ...)
```

只要终态只有一个出口，新增路径时就不可能忘记扇出。
另外压测结束时还有一层 `drain_all()` 兜底。

### 7. 调度器只看到队头，于是租户内部的优先级失效了

优先级队列最初实现成「每个租户一个 deque，每次从各队头里挑最好的」。
单测立刻挂了：一个后到的 `interactive` 请求排在先到的 `batch` 后面。

因为**优先级在同一个租户的队列内部是不单调的** —— 后进来的高优先级请求
会排在先到达的低优先级请求之后。只看队头，等于对同租户的请求退化成 FIFO。

修法不是「全都扫描一遍」（那在大队列上是 O(n) 每次出队），而是分清情况：

| 策略 | 排序键在租户内部是否单调 | 需要扫描范围 |
|---|---|---|
| FIFO | 是（按入队顺序） | 只看队头 |
| WFQ | 是（按虚拟开始时间） | 只看队头 |
| 优先级 + 老化 | **否** | 必须扫描全部 |

这是一个「性能优化把正确性优化没了」的典型例子。

### 8. 熔断的代价必须如实报告

上游故障率 70% 时，实测：

| 策略 | 本请求成功 | 上游提交 | 重试放大 |
|---|---|---|---|
| 无预算无熔断 | **65.4%** | 644 | 2.15× |
| 重试预算 10% | 30.3% | 205 | 1.05× |
| 预算 + 熔断 | **7.6%** | 219 | 1.12× |

熔断把本请求成功率从 65% 打到了 7.6% —— 这在监控上非常难看。

但那 65% 是**用 2.15 倍负载换来的**：上游已经七成故障，我们还在给它两倍多的请求，
其中大部分注定失败。熔断优化的从来不是「本请求成功率」，而是**系统整体健康度**：
停止向一个已知坏掉的依赖继续施压，把配额留给恢复。

§12.4 的原文就是「熔断的代价是它会拒绝掉本来可能成功的请求」。
如果不把这个代价如实打出来，读者会以为熔断是免费的。

### 9. 上游变慢，按 QPS 扩容完全无感

这是 `autoscale` 场景的核心。上游服务时间 ×3 之后：

* 本地容量从 5.33 掉到 1.78 RPS；
* **QPS 读数几乎没变**（因为 QPS 测的是「已经服务了多少」，而它恰好被我们
  自己的并发上限压着）——按 QPS 扩容的 HPA 一次都不触发；
* CPU 读数峰值 0.67，永远够不到 70% 的阈值 ——IO 密集服务的 CPU 与负载几乎无关；
* 队列深度触发 9 次扩容，派发量 129 → 253。

顺带一条：**本地并发不能扩到超过上游配额**。第一版让 autoscaler 一路扩到 44，
结果只是把队列从「本地看得见的 44」搬到了「上游看不见的内部队列」，
P99 反而更差。

### 10. 时间读的是仿真时钟，不是 `time.monotonic()`

整个仿真用**整毫秒**计数，不用浮点秒：

* 浮点累加会漂移（`0.1 + 0.2 != 0.3`），而漂移会让「同样输入跑两次结果不同」——
  场景无法回归，README 里的数字也就不可信；
* 所有模块在同一个 tick 内读到的 `now_ms` 完全相同，于是
  「同一时刻的多个事件」有一个由代码顺序决定的确定顺序，而不是由随机性决定。

另一个刻意的设计是**两个独立的 RNG**：

```
workload_rng   只生成流量（种子来自 scenario）
runtime_rng    服务时间抖动 · TTL 抖动 · 退避抖动
```

做 A/B 对照时（例如「同一批流量只换调度策略」），两边的**到达序列必须完全相同**，
否则你比较的是流量的差异而不是策略的差异。

## 已知边界

* **这是仿真，不是压测。** 它验证的是「设计在给定流量模型下是否收敛」，
  不是「真实硬件上的性能数字」。真去压测要集群、要额度、要几小时；
  仿真能做到的是**在压测之前把设计错误筛掉** —— 同样的结论可以在测试里被断言，
  `pytest` 三秒跑完。
* **仿真里每个命令都是原子的。** 虚拟时钟里没有真正的并发，所以
  「两个请求同时到达」有一个确定的处理顺序。这消除了竞态，让结论可复现，
  但也意味着**它测不出数据竞争** —— 真机上「两个实例同时读到过期租约」这类
  问题需要别的手段（见第十三章的 CAS 与幂等设计）。
* **上游模型是简化的。** 只有「并发槽位 + 服务时间分布 + 失败率」三个参数，
  没有 token 计费、没有流式首字节延迟、没有 provider 侧的速率限制。
  真机上最贵的那部分（token 成本）在这里没有建模。
* **分布式限流只有单机实现。** `RateLimiterSet` 是单进程的令牌桶，
  集群里会退化成「N 倍配额」。§6.3 讨论了三种做法（本地预取、中心化计数、
  配额分片），但本 Demo 只实现了最简单的那种，并在代码里标注了这个偏差。
* **没有流式响应的建模**（§3.4）。SSE 下连接要活几十秒，
  并发槽位在流式期间一直被占着，取消传播也更复杂。这里用「一次调用 =
  一个槽位占满服务时长」近似，结论方向一致，但具体数字会不同。
* **多租户只做到加权公平。** 没有硬隔离池、没有保底 + 借用（§15），
  也没有跨实例的配额协调。

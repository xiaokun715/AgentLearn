# risk-control-agent

> **风控 Agent Demo —— 传统风控与 Agent 是分层协作，不是替代关系**
>
> 在线决策链路（确定性、毫秒级、不调查）｜工具网关（权限 / 范围 / 预算 / 审计）
> ｜动态调查 Agent（假设驱动、路径自适应）｜固定工作流对照 ｜离线验证与策略运营

对应设计说明书：`../第十八章：风控 Agent 设计说明书.md`

---

## 一句话定位

> 传统风控回答的是「**这一笔是否符合已知风险模式**」。
> 它有明确的输入输出、稳定的性能、可审计的规则 —— 这些都不该被 Agent 取代。
>
> Agent 回答的是另外几个问题：
>
> * 这个风险事件**为什么**发生？
> * 还需要查什么才能确认？
> * 多个账号之间是什么关系？
> * 现有规则为什么没识别出来？
> * 这件事该**交给谁**、下一步做什么？
>
> 这些问题共同的特征是：**没有固定的输入输出，路径取决于中间结果**。

本 Demo 把两者放在同一个系统里跑，用同一批案件对比：

```
                       业务事件流
                            │
        ┌───────────────────▼───────────────────┐
        │  在线决策链路（不需要 Agent）             │
        │  特征 → 规则 → 模型 → 决策 |  3ms        │
        │  放行 / 验证 / 拦截 / 转人工              │
        └───────────────────┬───────────────────┘
                            │ 转人工（或规则与模型分歧）
                            ▼
        ┌───────────────────────────────────────┐
        │  工具网关（Agent 唯一的出口）            │
        │  ① 工具白名单 ② 权限 ③ 高危需审批        │
        │  ④ 实体范围   ⑤ 预算 ⑥ 全量审计         │
        └───────────────────┬───────────────────┘
                            ▼
        ┌───────────────────────────────────────┐
        │  调查 Agent（路径由证据决定）            │
        │  计划 → 调用 → 观测 → 更新假设 → 再计划   │
        │  输出：调查报告 + 处置**建议**           │
        └───────────────────┬───────────────────┘
                            ▼
        ┌───────────────────────────────────────┐
        │  离线评估（Agent 只能把假设推到候选）     │
        │  回放验证 → 人工确认 → 才能进规则         │
        └───────────────────────────────────────┘
```

**贯穿全篇的一条硬边界**：Agent 只能**建议**，不能**执行**。
处置、改规则、发布策略 —— 这三件事在 Demo 里由工具网关**结构性**地挡住，
不是靠提示词约束。

## 特性一览

| 主题 | 落地 |
|---|---|
| **在线链路是确定性的** | 特征 → 规则 → 模型 → 决策，实测 **3ms**，五次评估结果完全一致 |
| **规则与模型分歧时不选边** | 高规则分 + 低模型分 → `REVIEW`，把决定权交出去而不是「谁严听谁的」 |
| **规则要有比较方向** | `direction: above/below` —— 少了它，「注册 10 分钟内领券」会变成「注册超过 10 分钟」，对每一个老用户都命中 |
| **规则知道场景** | 促销期退款阈值上浮 —— 规则必须知道自己在什么场景里被评估（§6.2）|
| **工具网关六道关** | 白名单 / 权限 / 高危审批 / 实体范围 / 预算 / 审计，**没有旁路** |
| **实体范围约束** | 授权的是「实体 + 直接关联」，不是全库 —— 被污染的告警不该让 Agent 遍历用户库 |
| **审批是动作级** | 人工签发 `approval_id` 只授权**这一次调用**；同一个号不能用于另一个动作 |
| **改规则没有审批通道** | `update_rule_config` 申请审批直接抛 `PermissionError`，这条路径不存在 |
| **假设驱动的调查** | 观测 → 假设权重 → 下一步查什么，全部是确定性规则；模型不参与路径选择 |
| **证据极性** | 工具声明 `{假设: +/−}` —— 「设备图报异常」不可能同时支持「这是团伙」和「这是正常用户」|
| **先查证再查案例** | 上下文工具（历史案例）只在没有可做的检查时才上场：它回答「以前怎么处理」，不回答「这次是不是」 |
| **查不到 ≠ 没问题** | `INCONCLUSIVE` 只支持「数据不足」，不影响任何风险假设 |
| **没查过 ≠ 没问题** | 误报结论要求**所有**风险假设都被反驳，而不是「没有风险假设成立」|
| **证据冲突不下单边判断** | 3 条支持 + 1 条反驳不判 `REFUTED` —— 一条弱反证不该推翻三条强支持 |
| **Agent 只能提候选** | 风险模式只能推到 `CANDIDATE`；`VALIDATED` 需要离线回放 + **人工签字** |
| **候选策略必须报漏报** | 只报「误报下降」不报「漏报影响」的候选被直接拒回 |
| **固定工作流作为对照** | 同一批案件跑两种方式：实测固定流程在数据缺失时给出**错误结论** |
| **零外部依赖** | 只有 `pydantic` + `pyyaml`；LLM 由确定性 `ScriptedLLM` 扮演 |

## 快速开始

```bash
cd risk-control-agent

python -m app.main --list      # 看有哪些场景
python -m app.main all         # 全跑（约 1 秒）
python -m app.main paths boundary
python -m app.main tests       # 45 项断言，退出码即结果

python -m pytest               # 60 个单测
```

依赖只有两个：`pydantic` / `pyyaml`。

```bash
pip install -e .        # 或 pip install pydantic pyyaml
```

## 场景演示

| 命令 | 场景 | 看什么 |
|---|---|---|
| `online` | §1 | 三种事件的在线裁决；规则与模型分歧 → `REVIEW` |
| `investigate` | §4 | 一个案件的完整调查：假设演化、证据链、报告 |
| `paths` | §5 | **核心**：三个案件三条路径 + 固定流程对照 |
| `boundary` | §3.2 | **核心**：越权调用被拦、范围约束、审批是一次性动作 |
| `discover` | 方式二 | 未知风险发现：弱信号组合 + 离线回放把假设退回 |
| `strategy` | 方式三 | 误报分析 → 候选策略 → 不能发布 |
| `value` | §7 | 价值三层次与可验证指标 |
| `tests` | — | 45 项断言 |

### §5 三个案件三条路径（实测）

| 案件 | 裁判结论 | Agent 路径 | 步 | 固定流程 | 步 |
|---|---|---|---|---|---|
| 设备农场套利 | `CONFIRMED_RISK` | 账号→设备→图分析 | 3 | ✓ 同 | 4 |
| 商品质量退款（误报）| `LIKELY_FALSE_POSITIVE` | 账号→交易→设备 | 3 | ✓ 同 | 4 |
| 设备数据源不可用 | `INSUFFICIENT_EVIDENCE` | 账号→交易→设备→案例 | 4 | ✗ **`LIKELY_FALSE_POSITIVE`** | 4 |

**前两个案件的路径在第二步就分开了**：

```
① 账号画像 → 「新账号 + 等级 0 + 领券超阈」  → 下一步查设备
② 账号画像 → 「老账号 + 等级 4 + 历史订单 120」→ 下一步查交易明细
```

顺序不是人预先定义的，而是**证据决定的**。

### §5 固定流程错在哪（实测）

```
设备数据源不可用（2 次调用无返回）

  Agent 结论      : INSUFFICIENT_EVIDENCE   ✓
  固定流程结论     : LIKELY_FALSE_POSITIVE   ✗
  Agent 未覆盖维度 : ['H_SHARED_DEVICE：尚未被任何工具有效检验']
  固定流程未覆盖维度: []                      ← 它甚至说不出自己没查全
```

**这是最危险的一类错误**：它安静、可解释、看起来完全正常 ——
「未发现异常」和「查完没发现异常」在报告上长得一模一样。

注意 Agent 在这里**并不更快**（4 步 vs 4 步）。它的价值不是效率，
而是**能够说出自己没查全**。

### §3.2 权限边界（实测）

| Agent 想做的事 | 类别 | 风险 | 结果 |
|---|---|---|---|
| `apply_disposition` | WRITE | HIGH | ✗ `NO_PERMISSION` |
| `release_block` | WRITE | HIGH | ✗ `NO_PERMISSION` |
| `update_rule_config` | ADMIN | HIGH | ✗ `NO_PERMISSION` |
| `publish_strategy` | ADMIN | HIGH | ✗ `NO_PERMISSION` |
| 查询范围外的账号 | — | — | ✗ `OUT_OF_SCOPE` |

Agent 的权限集只有 `{risk:read, risk:graph, ops:write}` ——
**没有 `risk:enforce`，也没有 `risk:admin`**。这不是「暂时忘了加」，
它由启动自检在每次装配时断言。

人工审批之后：

```
grant_approval("apply_disposition", "APPROVAL_2026_1017_001") → 可以执行这一次
同一个审批号去调 release_block                              → 被拒
```

**审批的是「这一次调用」，不是「以后这类事你都可以自己做」。**

### §5.3 未知风险发现（实测）

现有规则一条都没命中（每个账号领券 3 次 < 阈值 5，退款率 40% < 阈值 55%，各自一台设备）。

```
候选模式 1：设备型号不可用
  命中 155，其中黑产 30  →  precision 0.194  →  NEEDS_MORE_DATA（被退回）

候选模式 2：设备型号不可用 + 注册时间聚集
  命中  35，其中黑产 30  →  precision 0.857  →  CANDIDATE
```

「设备型号不可用」有 125 个正常账号；「注册时间聚集」有 20 个正常账号；
但两者**同时命中**的只有 35 个，其中 30 个是黑产。

**Agent 擅长的不是发现某个信号，而是想到把两个弱信号组合起来。**
而「组合之后到底行不行」由离线回放回答，不由模型回答。

把它提升为已确认，需要人工签字：

```
confirm(pattern, reviewer="")                → PermissionError
confirm(pattern, reviewer="risk-expert-02")  → VALIDATED
```

### 方式三 策略运营（实测）

```
复盘样本        200 条人工审核过的告警，其中误报 100 条（50%）

场景      告警数  误报数  误报率
normal      100     20    20%
promo       100     80    80%    ← 误报集中在这
```

候选策略：为 `R003_REFUND_RATIO` 增加场景维度，促销期用不同阈值。

```
预期误报下降 62.4%    预期漏报上升 2.1%    ← 两个都必须报
```

把 `expected_fn_delta` 置零、只留「误报下降」的候选会被**直接拒回**：

```
✗ 拒回
   · 缺少必填字段 expected_fn_delta
   · 必须显式给出 expected_fn_delta —— 声称「零漏报代价」的放宽，通常是没算过
```

Agent 想发布它：`publish_strategy` → `NO_PERMISSION`。

## 关键设计取舍（这些是面试会追问的地方）

### 1. 一个工具能「区分」假设，不等于它「支持」全部假设

最早的工具声明只有一个 `targets: list[str]`，语义被简化成了
「工具报异常 → 列表里的假设全部被支持」。

于是设备图查出 7 个账号共用一台设备时，它**同时支持了**
`H_SHARED_DEVICE`（团伙）和 `H_LEGITIMATE`（正常用户）。

一个工具报异常，不可能同时支持「这是团伙」和「这是正常用户」。
根因是把两件事混成了一件：

| 概念 | 含义 |
|---|---|
| 工具能**区分**哪些假设 | 规划器用它决定「查哪个最值」 |
| 一次观测**支持/反驳**哪个假设 | 更新假设用它 |

修法是给每个工具声明带极性的映射：

```python
evidence_map = {"H_SHARED_DEVICE": "+", "H_BULK_REGISTER": "+", "H_LEGITIMATE": "-"}
```

`"+"` 表示「报异常即支持」，`"-"` 表示「报异常即反驳」，`NORMAL` 取反。

### 2. 「没查过」被当成了「没问题」

误报结论的门槛最初是「没有风险假设被支持」。但一个**从没被检验过**的假设
既不是 `SUPPORTED` 也不是 `REFUTED` —— 于是它被这句话放过去了。

实测后果：设备图不可用时，Agent 只查了账号和交易就宣布「误报」。

修法是两条：

1. 结论门要求**所有**风险假设都被 `REFUTED`，而不只是「没有被支持」；
2. 兜底结论区分「有维度根本没被检验」（→ `INSUFFICIENT_EVIDENCE`）
   与「证据自相矛盾」（→ `NEEDS_HUMAN_JUDGEMENT`）。

**「没查」归成「没问题」，是调查类系统最典型的假阴性** ——
而且它安静、可解释、看起来很正常。

### 3. 结论门和生成报告用了两套判据

更隐蔽的一层：`_conclusion_ready()`（决定循环是否结束）和 `_conclude()`
（生成报告）是两段独立的代码，它们对「什么时候算误报」的判断**不一致**。

于是当循环因为别的原因（比如空转计数）提前退出时，报告会给出一个
**比循环本身的判定更宽松**的结论 —— 一个从没查过的维度被当成了「没问题」。

两处判据不一致，是这类系统最难发现的一类 bug：单独测哪一处都是对的。

### 4. 一条弱反证推翻了三条强支持

假设状态的判定最初是：

```python
if len(refute) >= 1:      REFUTED
elif len(support) >= 2:   SUPPORTED
```

只要有一条反驳证据就判 `REFUTED` —— 于是「3 条支持 + 1 条反驳」被推翻。

在一个误报案例里，这个 bug 的表现是：正常用户的历史订单数（120 笔）
被算成了一个风险信号，产生 1 条反驳证据，最后把一个明确的误报报成了「转人工」。

修法是**证据冲突时不下单边判断**：

```python
if refutes >= 1 and refutes > supports:   REFUTED
elif supports >= 2 and refutes == 0:      SUPPORTED
elif supports or refutes:                 UNDECIDED
```

同一个 bug 还有另一半：`query_account_profile` 把「历史订单 120 笔」
写进了 `findings`。**那是一个正常的背景信号，不是风险信号。**
把背景当信号，会让一次本应中止的调查反向跑偏。

### 5. 规则的比较方向写反了

`R004_NEW_ACCOUNT_CLAIM` 的语义是「注册后 10 分钟内领券」，但规则引擎对
所有规则都用 `value > threshold`：

```
minutes_since_register = 999  >  10  →  命中
```

于是这条规则对**每一个老用户**都命中。这类 bug 不会报错、不会崩溃，
只会让规则**反着生效** —— 而且从告警量上看，它显得「规则很灵敏」。

修法是给规则加显式的 `direction: above | below`。
教训：**任何比较都必须能回答「大于和小于分别在表达什么」**。

### 6. 配置写对了，但没有接线

`PlatformConfig.max_tool_calls` 声明了、启动自检也校验了它 ——
但调查器一直用的是模块级的默认预算。**这个配置从来没有生效过。**

它只在跑一个「本来会超预算」的场景时才暴露出来：测试断言
`tool_calls <= 3`，实际得到 4。

这类「配置看起来生效了、其实没有」的问题，靠读代码很难发现 ——
因为代码里确实**读**了那个字段（在自检里）。检测它的办法是：
**让配置真的去改变一个可观测的结果**，而不是只校验它合法。

### 7. 数据源查询顺序反了，导致调查结论完全颠倒

`RiskWorld.add_device()` 最初直接覆盖设备对象：

```python
self.devices[device_id] = DeviceProfile(...)
```

而世界构造时是「先 `add_user`（建立关联）、后 `add_device`（补型号）」，
于是关联被**清空** —— 设备图返回空列表，「共享设备」被判为正常，
一次本该确认风险的调查给出了误报结论。

它不报错，只是安静地给出相反的结论。
修法是 `add_device` 保留已有的账号关联（更新而非替换）。

### 8. 上下文工具不该和「能区分假设的检查」抢位置

历史案例检索不区分假设 —— 它回答的是「这类事以前怎么处理的」，
不回答「这次是不是这种情况」。

早期版本给它一个固定的高分（「已有假设被支持时，案例检索值 1.0」），
结果是：**还有一个维度没查，规划器先去检索历史案例了**。

修法是把它降级为兜底：只有在**没有可做的检查**时才上场。

### 9. 固定工作流不是「更差」，而是「不知道自己缺什么」

值得说清楚的一点：固定工作流在前两个案件里跑出的结论**都是对的**。

它的问题只在数据缺失时暴露 —— 但那时它给出的错误结论与正确结论
**在报告上长得一模一样**：都是「未发现异常」。

这也是本 Demo 把对照组实现出来的原因：一个没有对照组的
「Agent 更好」的主张，是没法验证的。

### 10. 让模型少做事

模型在这个 Demo 里只出现在两个地方：

| 环节 | 是否需要模型 |
|---|---|
| 在线决策（特征/规则/打分/处置）| 不需要 |
| 调查路径选择 | 不需要（规划器按假设权重算，可解释可回归）|
| 证据 → 假设的更新 | 不需要（查表规则）|
| 结论判定 | 不需要（确定性判据）|
| 把证据归纳成人能读的报告 | **需要** |
| 提出新的风险模式 | **需要** |

这个分布本身就是一条论点：**Agent 的价值不等于「到处都用大模型」**。
真正需要模型的是**开放式的归纳**和**跨域的联想**，
不是权限判断，也不是路径选择。

## 已知边界

* **数据是手工构造的**。它保证结论可复现，但**不会**暴露真实风控数据的脏乱
  （字段缺失、时间戳漂移、同一行为多种成因）。接真机时 `sim.py` 要整个换掉。
* **风险模型是线性 + 人为权重**。真机上应该是 GBDT/深度模型 + 特征平台；
  本 Demo 只关心「模型输出怎么被两条链路使用」。
* **意图与实体识别没有建模**。告警直接给出 `entity_id`，真机上这一步
  （从事件里定位到要调查的实体）本身就需要工程投入。
* **离线回放用的是内置标注集**，不是真实的历史回放平台。
  `recall/precision` 的绝对值没有意义，有意义的是**「回放把假设退回了」这件事发生了**。
* **没有多 Agent 协作**。本 Demo 刻意用单 Agent + 受控工具 ——
  在调查场景里，多 Agent 带来的通信开销往往大于收益；真需要拆分的信号是
  「不同子调查需要不同的权限域或不同的模型」。
* **时间与成本是仿真值**。`latency_ms` 是各工具声明的常量之和，
  不是真实网络延迟。价值量化那一节给的是**方法**，不是结论。

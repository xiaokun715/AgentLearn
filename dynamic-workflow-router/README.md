# dynamic-workflow-router

> **动态 Workflow 与 Agent 路由 Demo —— 让「谁来干活」成为一次可解释、可沉淀的决策**
>
> Agent Pool（子 Agent ＋ 已生成模板）｜意图识别｜路由引擎（五终点）｜现场编排
> ｜Workflow Validator｜黑板书执行器｜带标签的模板库｜保存-丢弃闭环

对应设计说明书：`../第十七章：动态 Workflow 与 Agent 路由设计说明书.md`

---

## 一句话定位

> 一个用户 query 进来，系统要回答三个**不同**的问题：
>
> 1. **用户想要什么？**（意图识别）
> 2. **谁来干？**（路由引擎）
> 3. **怎么拆、按什么顺序干？**（编排）
>
> 把这三个问题混在一起，是这类系统最常见的坏味道：意图识别器里塞满路由规则，
> 路由规则里塞满编排知识，最后没人能说清「为什么这次走的是这条路」。

本 Demo 把它们切成三层，并且让**每一层的产物都是结构化数据**：

```
query
  │
  ├─ ① 意图识别 ──> Intent {名字, 能力集合, 步数估计, 置信度}
  │                  路由与编排从此**不再需要理解自然语言**
  │
  ├─ ② 路由引擎 ──> RoutingDecision {五种终点之一, 候选评分明细, 理由}
  │                  │
  │      ┌───────────┼───────────┬──────────────┬─────────────┐
  │      ▼           ▼           ▼              ▼             ▼
  │   直连子 Agent  命中已有模板  现场编排      澄清          拒绝
  │                             │
  ├─ ③ 编排 ────────────────────┘
  │      能力→Agent 映射 → 数据流闭合 → 依赖排序 → 校验 → 修复
  │
  └─ ④ 执行 ──> 黑板书 + 步骤轨迹（耗时按**关键路径**算）
                │
                └─ ⑤ 模板处置 ──> 用户选择 [保存 / 丢弃]
                                    │
                                    └─ 带标签入库 → 下次相同意图直接命中
```

## 特性一览

| 主题 | 落地 |
|---|---|
| **Agent Pool** | `pool/agents.py`：14 个子 Agent，声明**能力标签 + 数据流契约**（``reads``/``writes``）+ 成本/时延/风险/健康度 |
| **池子只认能力，不认名字** | 路由与编排代码里**没有一处**提到具体 Agent 名 —— 重命名一个子 Agent 不需要改一行路由规则 |
| **模板也是池子成员** | `pool/templates.py`：对路由引擎来说，子 Agent 与模板是**同类候选**，用同一把尺子评分 |
| **规则优先的意图识别** | 关键词命中 → 直接出结论；命不中 → LLM 兜底（打折置信度）；再不行 → `UNKNOWN` |
| **步数是算出来的** | `estimated_steps` = 覆盖 `required_capabilities` 最少需要几个 Agent —— 一个事实，不是主观判断 |
| **说不清就澄清** | 置信度低于阈值 → `CLARIFY`，而不是硬路由。「问一句」比「路由错」便宜得多 |
| **五终点路由** | `DIRECT_AGENT` / `EXISTING_TEMPLATE` / `COMPOSE_NEW` / `CLARIFY` / `REJECT` |
| **统一评分** | `score = w_cov·覆盖 + w_intent·意图 + w_rel·可靠 + w_reuse·复用 − 成本 − 延迟 − 风险 − 步数` |
| **部分覆盖 = 不合格** | 只覆盖 2/6 能力的直连 Agent 会被标为 blocked —— 让它自信地回答一个它没被设计来回答的问题，比明确失败更糟 |
| **平滑成功率** | 拉普拉斯平滑 `(s+1)/(n+2)`：1 次成功 1 次 → 0.67，39 次成功 42 次 → 0.91 |
| **强制 Workflow 模式** | 用户显式选择时，**即使库里有完全匹配的模板也照样现场生成** —— 「强制」就是强制 |
| **确定性编排器** | 同一意图 → 同一份 DAG（用结构指纹可验证）。LLM 提议是**补充路径**，不是主路径 |
| **数据流闭合** | `needs` / `produces` 显式建模，并在生成阶段就闭合；缺失的生产者会被**自动补进去** |
| **数据流有序 ≠ 闭合** | 键有人产出但产出者不在依赖链上 → `DATA_FLOW_UNORDERED`。这类 DAG「碰巧能跑通」，一并行就崩 |
| **七项校验** | Agent 存在 / 依赖完整 / 无环 / 数据流闭合与有序 / 能力覆盖 / 预算 / 风险与副作用 |
| **能修就修** | `repair()`：丢弃悬空依赖、丢掉可选的坏步骤、按数据流重排解环；修不好才报错 |
| **黑板书执行** | 子 Agent 之间**不直接调用**，只通过共享上下文耦合 —— 编排器才能自由重排与替换 |
| **关键路径计时** | 总耗时取 DAG 最长路径，不是各步之和（实测 3800ms vs 求和 5000ms）|
| **失败分两种** | `optional` 步骤失败只跳过；必选步骤失败先重试再中断。**默默少做一步**是编排系统最危险的失败模式 |
| **模板标签** | 生成人 / 生成时间 / 来源 / 域 / 意图 / 风险 / 自定义标签 / 运行统计（跑过几次、成功率、平均时延）|
| **保存质量门** | 五道：标签齐备 → **先成功跑过一次** → Agent 还在 → 结构不重复 → 容量 |
| **结构去重** | 同一份 DAG 换个名字还是同一份 —— 指纹只哈希结构与数据流。重复不是丢弃，而是**合并标签** |
| **版本演进** | 旧版标记 `DEPRECATED` 并指向新版；**保留**旧版，因为历史轨迹还引用着它 |
| **失效检测** | Agent 下线 → 引用它的模板自动标 `BROKEN` 且不再被路由 |
| **热配置** | `configs/agents.yaml` 只允许**覆盖**已有 Agent，不允许凭空造一个 |
| **启动自检** | 10 项：能力覆盖完备、每个 `reads` 都有人产出、副作用必须是高风险、权重自洽、澄清阈值可达…… |
| **零外部依赖** | 只有 `pydantic` + `pyyaml`；LLM 由确定性 `ScriptedLLM` 扮演 |

### §6 路由决策的可解释性（实测）

query「SRS 测试失败了，帮我定位一下根因」→ 意图 `troubleshoot_failure`（6 项能力）

```
 ✓ 模板:测试失败标准排障流程   score=3.729 覆盖=1.00 意图=1.00 可靠=0.91 成本=8.5 步数=6
   Agent:log_collector        score=2.058 覆盖=0.17 意图=1.00 可靠=1.00 成本=1.0 步数=1
     ⛔ 只覆盖 17% 的能力，回答会不可信
   Agent:config_inspector     score=2.033 覆盖=0.17 意图=1.00 可靠=1.00 成本=1.0 步数=1
     ⛔ 只覆盖 17% 的能力，回答会不可信
   Agent:report_writer        score=1.983 覆盖=0.17 意图=1.00 可靠=1.00 成本=1.0 步数=1
     ⛔ 只覆盖 17% 的能力，回答会不可信
   …
   → 7 个候选，6 个被排除
```

**没有 if-else，只有一张评分表。** 覆盖权重最高（2.0），因为能力覆盖是硬约束。

### §7.2 三条路径（实测）

| 路径 | 终点 | 步数 | 编排成本 | 总耗时 | 产生新模板 |
|---|---|---|---|---|---|
| ① 直连 | `DIRECT_AGENT` | 1 | 0ms | **250ms** | 否 |
| ② 复用模板 | `EXISTING_TEMPLATE` | 6 | 0ms | 3800ms | 否 |
| ③ 现场编排 | `COMPOSE_NEW` | 3 | **40ms** | 1090ms | **是** |

编排成本只付一次 —— 现场生成之后保存，再遇到同样的意图就走第 ② 行。

### §10.2 关键路径 vs 朴素求和（实测）

6 步排障模板：`log_collector(300) → log_analyzer(500) → …`

```
关键路径：3800ms          ← 实测
朴素求和：5000ms          ← 错算
分层执行：层1['s1','s3','s4'] → 层2['s2'] → 层3['s5'] → 层4['s6']
```

**编排的意义就是让互不依赖的步骤并行**，求和会把并行的收益算没 ——
于是「编排比直连慢」这个结论会永远是假的。

### §8.2 / §9.1 模型提议的六种问题（实测）

| 模型提议的问题 | 结果 | 处理 / 拦截 |
|---|---|---|
| 正常提议 | ✓ 放行 | OK |
| 漏写依赖 | ✗ 拦下 | `DATA_FLOW_UNORDERED` |
| 写出环 | ✗ 拦下 | `CYCLE` |
| 发明不存在的 Agent | ✓ 放行 | 提议阶段就被过滤掉（校验器根本看不到）|
| 偷偷插入写环境的步骤 | ✗ 拦下 | `DATA_FLOW_BROKEN；RISK_EXCEEDS_BUDGET；SIDE_EFFECT_STEP` |
| 一口气排十几个步骤 | ✗ 拦下 | `BUDGET_COST；BUDGET_STEPS` |

**两道防线各管一段**：提议阶段过滤掉不存在的 Agent，校验器拦住结构性问题。

## 关键设计取舍（这些是面试会追问的地方）

### 1. 「部分覆盖」的直连 Agent 必须被排除

最初的评分里，一个覆盖 1/6 能力的 `log_collector` 靠「便宜 + 快」排到了第二位
（score 2.058），仅次于模板（3.729）。如果阈值调低一点，它就会被选中。

但**一个 Agent 只覆盖了 1/6 的能力，却会自信地给出一个完整回答** ——
它被设计来读日志，你却问它根因是什么，它会把自己知道的那部分当成全部。
这比明确失败更糟：调用方拿到的是一个看起来专业、实际上残缺的结论。

所以直连候选的门槛是**覆盖率必须等于 1.0**，不满足的直接标 `blocked`。

这不是一条「更严格」的规则，而是一条**关于失败模式的判断**：
在 Agent 系统里，**无声的部分成功比响亮的失败危险得多**。

### 2. 拉普拉斯平滑：别让一次运气压过四十次证据

一份刚跑成功一次的新模板，原始成功率是 **100%**。它会立刻在评分上压过
一条跑了 42 次成功 39 次的成熟模板（92.9%）—— 而两者的证据量差了 40 倍。

```python
def smoothed_success(successes, runs):
    return (successes + 1) / (runs + 2)
```

| | 原始 | 平滑后 |
|---|---|---|
| 1 次成功 1 次 | 100% | **66.7%** |
| 39 次成功 42 次 | 92.9% | **90.9%** |

排序终于反映了「证据够不够」，而不是「运气好不好」。

同理，**复用奖励用对数增长而不是线性**：线性的「用得越多越优先」会让模板库
锁死在最初的几条上 —— 新模板永远没有机会被验证，于是永远没有数据证明它更好。

### 3. 「数据流闭合」和「数据流有序」是两件事

校验器一开始只有「闭合」检查：每一步的 `needs` 都要有人产出。

结果**漏掉了一整类 bug**：某个模型提议故意删掉了所有 `depends_on`，
但因为它生成的步骤 id 恰好是按依赖顺序编号的（m1, m2, m3），
拓扑排序按 id 一排，居然就通过了。

可是这份 DAG **只是碰巧能跑通**。调度器没有被要求按 id 顺序执行；
一旦它并行跑 m1 和 m2，m2 就会读到空的 `metrics`。

所以补了第二个检查：

```
键有人产出 ≠ 产出者在本步的依赖链上
```

前者是**闭合**，后者是**有序**。这两者在串行执行下表现一样，
在并行执行下完全不同 —— 而编排系统的全部意义就是并行。

### 4. `repair()` 不能修改调用方手上的那份

测试里出现了这个断言失败：

```python
template = _two_step(platform)
template.steps[1].depends_on = ["a", "ghost_step"]
repaired, report = validator.repair(template)
assert template.steps[1].depends_on == ["a", "ghost_step"]   # ← 失败
```

`repair()` 原地改了传进来的对象，于是「原始模板」在调用之后神秘地变了。
而调用方往往还持有它，并在后面拿它和修好的版本做对比。

修法是 `repair()` 一进来就 `model_copy(deep=True)`。
这类 bug 的隐蔽之处在于：**在只有一条调用路径时它完全看不出来**。

### 5. 「强制生成」就是强制，即使库里有现成的

`FORCE_WORKFLOW` 模式下，如果池子里已经有一条完全匹配的模板，
一个「聪明」的实现会说：「已经有更省的选择了，我帮你复用吧」。

但用户选这个模式，通常是想看「**现在能编出什么**」，或者要做 A/B 对照。
偷偷复用会让这个语义彻底失效 —— 用户以为自己在评测生成质量，
实际上看到的是历史模板的复现。

所以：**强制模式无条件现场生成**。至于它生成出来的东西和已有模板重复，
那由保存时的结构去重去处理（实测会走 `REJECT_DUPLICATE` 并合并标签）。

一个相关的取舍：**「强制」不等于「绕过校验」**。生成的模板照样要过七项校验，
高风险意图（`config_fix`）在强制模式下也照样会被拦下。

### 6. 池子不能共享模块级的默认值

`AgentPool()` 一开始是把 `BUILTIN_AGENTS` 里的对象直接 `register` 进去的。
于是 `pool.set_health("log_collector", OFFLINE)` **改到了全局**。

表现是典型的「单独跑某个测试能过，一起跑就挂」：
测试 A 把一个 Agent 下线，测试 B 新建的池子里它也还是下线的，
而 B 失败的位置离原因很远。

修法是在 `AgentPool.__init__` 里 `model_copy(deep=True)`。
**默认值必须是「每次取一份新的」，不能是「共享一份」** ——
这条规则对任何可变的模块级常量都成立。

### 7. 执行器里最危险的失败模式是「默默少做一步」

一个编排系统如果在上游失败时「跳过那一步继续往下跑」，
用户拿到的会是一个**看起来完整、实际缺了一块**的结论。

所以本 Demo 把失败分成两种：

| 步骤类型 | 失败处理 |
|---|---|
| 必选（默认）| 先重试，重试完再失败则**中断**，下游全部标 `BLOCKED` |
| `optional=True` | 跳过，**并且其下游照常执行** |

第二条容易被写错：`optional` 的语义就是「不做也能继续」。
如果跳过它会让下游全部阻塞，那它就不是可选的，而是「必选但允许失败」——
那是另一回事，应该由步骤自己的降级逻辑处理，而不是靠 `optional` 掩盖。

### 8. 失效检测：模板库最大的一个坑

子 Agent 下线了，模板却还引用着它。等到有人真的命中这条模板时才报错 ——
而那时它已经在生产上跑了一半。

所以池子变更之后必须重新审计模板库：

```
Agent 下线 → audit_health() → 引用它的模板标 BROKEN
          → 路由不再选中（实测：受影响模板全部从候选里消失）
```

实测一次「下线 `code_reader`」影响了两条模板（种子模板 + 现场生成的），
它们当场变成 `BROKEN` 并从路由候选里消失。

### 9. 编排器的确定性是模板能被沉淀的前提

如果每次都让模型自由发挥，那么「这个意图的最佳编排」永远无法沉淀 ——
每次生成的形状都不同，模板库里会攒下一堆同义但不同的 DAG，
结构去重也就永远命不中。

所以主路径是**确定性规划器**：同一个意图 → 同一份 DAG（可用结构指纹验证）。
LLM 的价值在于**覆盖面**（它能提出人没预料到的步骤组合），
而不是**稳定性**。它是补充，且必须过校验。

### 10. 意图的产物不是「一个名字」

如果意图识别只输出一个名字（`troubleshoot_failure`），那么下游要么
重新解析一遍 query，要么被迫把业务知识塞进路由规则里。

所以本 Demo 的意图是一份结构化数据：

```python
Intent {
  name: "troubleshoot_failure",
  required_capabilities: ["log_read", "log_analysis", "env_check",
                          "config_check", "root_cause", "report"],
  estimated_steps: 6,        # = 覆盖这些能力最少要几个 Agent
  confidence: 0.75,
  entities: {"subject": "SRS"},
  status: RESOLVED,
}
```

**路由与编排从此都不需要理解自然语言** —— 它们只处理能力集合。
而且 `estimated_steps` 是一个**算出来的事实**，不是「模型觉得复杂」：
后者会让同一句话今天走直连、明天走编排，无法回归。

## 已知边界

* **意图识别是关键词规则 + 一个脚本化的兜底**。真机上这里应该是分类模型或
  小模型 + 槽位抽取，`entities` 也该由 NER 产出。本 Demo 的重点在
  「意图的产物是什么形状」，不在「怎么识别」。
* **编排器只会生成 DAG，不会生成分支与循环**。真实场景里的
  「如果环境异常就跳过日志分析」这类条件边没有建模 ——
  那需要一套条件表达式与求值器，会显著放大校验器的复杂度。
* **模板库是进程内的**。没有持久化、没有并发写入、没有跨实例的版本协调。
  真机上它应该是一个带乐观锁的存储，`version` 字段就是为此预留的。
* **只有单租户视角**。真实系统里模板的可见性、审批、跨团队共享都需要权限模型
  （标签里的 `author` 是它的最小种子）。
* **执行是同步的、串行的**。`_groups()` 算出了可并行分组并用于计时，
  但实际执行仍按拓扑序串行 —— 这是为了让演示可复现。换 `ThreadPoolExecutor`
  即可真并行，但要把「同层步骤共享黑板书」的写入冲突一起处理掉。
* **没有真实的失败注入框架**。`RuntimeOptions.fail_steps` 是手工指定的，
  真机上应该由混沌工程工具驱动（见第十二章的重试与熔断设计）。

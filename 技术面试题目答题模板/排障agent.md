# 排障 Agent 核心原理与诊断架构

> 核心问题：排障 Agent 如何定位根因、主动调查、验证假设，以及如何将诊断过程做成可靠的工程系统。

## 1. 排障 Agent 和普通的日志分析 Agent 有什么区别？

```
普通日志分析 Agent 的核心是理解已有日志，提取异常并生成原因分析；排障 Agent 则需要进一步决定下一步调查什么、调用什么工具、如何区分多个候选根因，以及何时可以确认结论。

例如在 AI4Test 中，SRS 测量指标异常可能来自环境干扰、功能配置、基带软件版本或测试用例。仅凭一段日志通常无法直接确定根因。

因此，我会将排障过程设计成一个闭环：故障识别 → 假设生成 → 诊断规划 → 工具调查 → 证据验证 → 根因确认或继续调查 → 修复与复测。

两者的关键区别不在于有没有调用工具，而在于是否具备主动调查、竞争性假设管理和验证闭环。即使最终没有找到根因，也应该输出已经确认的事实、未排除的假设、证据缺口和下一步调查建议。
```

## 2. 排障 Agent 为什么不能直接让 LLM 分析所有日志并给出根因？

```
核心问题是信息不完整、日志噪声大，以及多个根因可能产生相似的异常表现。

例如测试失败日志中出现指标异常，LLM 可能根据历史案例推断是版本回归，但真实原因也可能是运行时配置未生效。模型生成的解释看起来合理，并不代表它得到了当前故障的证据支持。

我的设计是先对日志进行结构化解析，提取错误码、异常事件、时间戳、测试步骤和关键参数，再结合环境状态、版本信息和领域知识建立候选根因。

随后由诊断规划器决定下一步调查动作，验证器根据新证据更新候选假设。对于没有充分证据支持的根因，只能标记为候选，而不能直接作为最终结论。

因此，LLM 主要负责语义理解、假设生成和复杂信息关联；确定性规则负责已知错误检测和约束校验；工具负责获取真实数据；验证器负责检查结论是否有充分依据。
```

## 3. 排障 Agent 如何进行根因分析？如何区分故障现象、直接原因和根本原因？

```
我会将根因分析拆成三个层次。

第一层是故障现象，即系统实际观察到了什么，例如测试指标不符合预期、某个断言失败或者设备连接中断。

第二层是直接原因，即哪个组件或执行环节出现了异常，例如运行时配置与预期不一致。

第三层是根本原因，即为什么该环节会发生异常，例如配置下发流程中的某个条件判断错误，导致配置没有真正生效。

工程上，我会先从失败节点和日志中提取异常事实，再沿调用链、配置链路、版本变更和依赖关系向上追踪。每一步都要关联具体证据，而不是根据异常发生的位置直接认定根因。

例如，测试节点失败不等于测试框架存在缺陷；配置不一致也不一定意味着配置模块本身有问题，还可能是上游请求、权限或者状态同步造成的。

最终报告需要明确当前定位到了哪一层，以及根因是否经过验证。如果只能定位到模块级别，就不能把它包装成已经确认的代码级根因。
```

## 4. 排障 Agent 如何管理多个候选根因？如何避免过早下结论？

```
我会采用竞争性假设机制，而不是让 Agent 始终围绕一个初始判断进行调查。

例如，对于一个 SRS 测试失败，可以同时维护环境异常、配置未生效、版本回归和用例错误等假设。每个假设都记录支持证据、反对证据、缺失证据和验证状态。

当新证据到达时，系统更新各个假设的优先级。如果发现运行时配置正常，就降低配置未生效假设的优先级；如果基线版本在相同条件下通过，而新版本稳定失败，就提高版本回归假设的优先级。

这里需要特别区分没有支持证据和已经被排除。缺少证据不意味着假设错误，只有满足明确的排除条件，才能将其标记为已排除。

此外，我会引入反证检查：不仅要求 Agent 寻找支持当前判断的信息，还要求它识别哪些观测结果可能推翻该判断。

这样可以减少初始假设错误后不断自我强化的问题，也让最终结论更加可审计。
```

## 5. 排障 Agent 如何决定下一步调查什么？如何实现动态诊断规划？

```
我会将诊断规划设计成一个根据当前证据动态调整的决策过程，而不是预先写死所有排查步骤。

首先，根据故障现象生成候选根因；然后分析不同假设之间的关键差异，寻找能够区分这些假设的调查动作。

例如，怀疑配置未生效时，查询运行时配置可能比重新执行整个测试更有价值；怀疑版本回归时，则可以优先查询版本变更记录和基线测试结果。

动作选择需要综合考虑几个因素：预期信息增益、执行成本、历史成功率、工具依赖和操作风险。可以先用启发式评分实现，再根据历史故障数据逐步引入更精细的优化策略。

同时，规划器需要处理动作依赖。例如，必须先完成环境检查，才能安全执行某些恢复操作；多个互不依赖的日志查询则可以并行执行。

每轮工具返回结果后，Agent 都会更新诊断状态并重新规划。如果证据不足就继续调查；如果达到验证标准就结束；如果预算耗尽或关键证据不可获取，就输出未确定结论并转人工。
```

## 6. 如何利用 RAG 帮助排障？普通 RAG 为什么不够？

```
在 AI4Test 中，RAG 的价值不仅是检索相似故障文档，还要为根因分析提供领域约束、历史线索和验证依据。

我会根据查询类型选择不同的检索方式：错误码和专有名词适合关键词检索，语义相似的故障描述适合向量检索，版本和配置等结构化信息适合 SQL，功能、参数、协议流程和缺陷之间的关系则可以通过图检索查询。

但检索到相似案例并不意味着当前故障具有相同根因。因此，我会区分历史案例、当前观测证据和待验证假设。

进一步可以建立根因—证据关联图，将故障事件、异常现象、候选根因、日志证据、版本差异和验证动作关联起来。检索负责提供线索，诊断规划器负责决定如何验证，验证器负责判断证据是否足够。

此外，知识库更新需要考虑文档版本、索引一致性和历史案例的有效性。已经失效的修复方案不能因为历史上出现过，就继续作为高可信度建议。
```

## 7. 如何设计排障 Agent 的评估体系？如何判断它真的比普通方案更好？

```
我不会只用最终回答是否正确来评估排障 Agent，因为它可能碰巧猜对根因，却执行了大量无效工具调用，也可能给出正确的诊断结论但没有提供可追溯证据。

我会建立包含已确认根因的历史故障 Benchmark，记录故障现象、当时可获取的日志、版本和环境信息，并要求 Agent 在不知道最终根因的情况下完成诊断。

评估指标分为四类。

第一是诊断准确性，包括根因 Top-1 准确率和 Top-k 召回率。

第二是诊断效率，包括平均诊断时间、工具调用次数和无效调用率。

第三是证据质量，包括证据覆盖率、关键证据引用准确性，以及是否正确处理反证。

第四是闭环效果，包括根因验证率、修复成功率、复测通过率和错误修复率。

实验上，我会与规则基线、固定 Workflow 和单次 LLM 分析方案进行对比，并尽可能控制模型、输入信息和测试集的一致性。

这样才能判断收益究竟来自动态规划、检索增强、验证机制，还是仅仅来自使用了更强的模型。
```

# 03 · 排障 Agent 工程实现与可靠性

> 核心问题：如何把诊断能力落到可恢复、可审计、可控制成本的生产级 Agent 系统中。

## 8. 排障 Agent 如何设计 Runtime 和状态管理？如何支持长任务恢复？

```
排障任务通常涉及多轮工具调用、异步执行、设备资源竞争和人工审批，因此不能只依赖 LLM 的上下文窗口保存整个过程。

我会在自研 Agent Runtime 中维护结构化的诊断状态，包括当前故障任务、候选根因、证据索引、调查计划、工具执行记录、预算和恢复状态。

诊断过程可以采用状态机管理，例如初始化、调查中、待验证、已确认、待恢复、复测中和已关闭。每个关键动作完成后，持久化相应状态，以便进程异常退出后从最近的有效状态恢复。

工具执行也需要独立的可靠性机制，包括参数校验、超时、有限重试、幂等控制和结果核验。特别是重启设备或修改配置等有副作用的操作，不能因为调用超时就直接重复执行，而应先检查上一次操作是否已经生效。

另外，我会分别设置时间、工具调用和资源预算，防止 Agent 陷入无限调查。

这样，模型负责动态决策，Runtime 负责状态、执行和资源约束，两者的职责是分离的。
```

## 9. 排障 Agent 应该如何处理失败后的恢复？如何避免把恢复成功误认为根因已解决？

```
我会将故障诊断、恢复执行和修复验证拆成三个不同的阶段。

首先是根因诊断，确认问题发生机制及其证据。然后根据根因类别选择对应的处置流程，例如环境恢复、用例修复、配置修正或缺陷升级。最后通过定向复测验证处置效果。

这里需要区分三个状态：根因是否确认、修复是否完成、复测是否通过。它们不能合并成一个简单的成功或失败标志。

例如，设备重启后测试通过，只能说明当前测试恢复正常，并不能直接证明根因就是设备状态异常。重启可能暂时掩盖了真正的软件问题。

因此，我会尽可能保留原始故障证据，在修复后检查关键状态是否恢复，并通过针对性的复测验证故障是否消失。如果有条件，还可以进行基线对照或重复测试，排除偶然通过的情况。

如果复测仍然失败，Agent 应将新证据反馈到诊断状态，重新评估原有假设，而不是不断重复同一种恢复操作。
```

## 10. 排障报告应该包含什么？如果最终没有找到根因怎么办？

```
我会将诊断报告设计成结构化交付物，而不是让 LLM 在流程结束时自由总结一段文字。

报告分为几个核心部分：故障摘要、任务和环境信息、异常事实、根因分析、证据链、排查过程、处置建议、验证结果、风险与遗留问题，以及后续行动计划。

如果找到了根因，需要明确根因描述、影响范围、支持证据、反对证据、根因验证状态和后续修复方案。同时，区分根因已确认、修复已完成和复测已通过三个状态。

如果没有找到根因，则需要说明已经确认的事实、仍然成立的候选假设、已排除的方向、尚缺少的关键证据，以及为什么无法继续调查。

例如，当前无法区分配置未生效和版本回归时，报告应明确指出缺少哪项运行时配置记录，以及补充该记录能够区分哪些假设，而不是只写一句建议人工处理。

在工程实现上，我会让排障 Agent 输出结构化诊断结果，由独立的 Report Builder 负责组装报告，并在发布前校验证据引用、状态一致性和结论可信程度。

即使未找到根因，报告仍然应该帮助下一位工程师从已有进度继续调查，避免重复劳动。
```

## 04 · 高级设计与系统优化

> 核心问题：如何让排障 Agent 不只是能工作，还能持续提高诊断效率和可靠性。

## 11. 如何让排障 Agent 从历史故障中持续进化？

```
我认为排障 Agent 的持续进化，不应该只是保存历史对话或者不断修改 Prompt，而应该围绕诊断错误建立可评估的优化闭环。

首先，将已经确认根因的历史故障沉淀为结构化案例，包含故障条件、关键证据、验证动作、最终根因和修复结果。

其次，对诊断轨迹进行失败归因。例如，错误可能来自候选根因生成不准确、知识检索失败、诊断动作排序不合理、反证处理不足，或者停止条件设置不当。

不同问题需要采用不同的优化手段：检索问题优化索引和召回策略，规划问题优化动作评分，证据问题优化验证机制，工具问题则改进接口和执行控制。

最后，在固定 Benchmark 上评估改进前后的根因准确率、诊断耗时、无效工具调用和错误修复率。通过门槛后再发布，避免新策略改善某一类故障，却导致其他故障的诊断能力下降。

在积累足够的高质量数据之前，我会优先采用规则、启发式策略和离线评估，不会为了体现技术深度就直接引入强化学习。
```

## 12. 多 Agent 排障如何分工？为什么不直接让一个 Agent 自己调用所有工具？

```
我不会仅仅因为工具数量多，就把系统拆成多个 Agent。是否拆分，主要取决于职责边界、上下文差异、并行收益、权限隔离和维护成本。

在 AI4Test 中，日志分析、环境诊断、版本分析和领域知识分析可以作为相对独立的能力。它们可以并行收集不同类型的证据，再由根因协调器统一管理候选假设和诊断计划。

为了避免多个 Agent 重复调查，我会使用共享的证据索引和结构化诊断状态，而不是让它们仅通过自然语言互相交流。每个诊断模块都需要返回支持证据、反对证据、缺失信息和建议动作。

同时，主协调器负责控制依赖关系。例如，独立的日志查询可以并行执行，但依赖前一步结果的调查需要串行；可能争抢同一设备的操作则需要资源锁或调度约束。

如果某项能力逻辑简单、没有独立上下文需求，直接作为主 Agent 的工具或模块反而更合适。多 Agent 的价值在于改善职责隔离、并行效率和诊断质量，而不是增加系统复杂度。
```

准备建议： 如果面试时间有限，优先深入掌握第 4、5、7、8、9 题。这几题分别覆盖根因假设管理、动态诊断规划、量化评估、Runtime 可靠性和故障闭环，能够形成一条完整的高级排障 Agent 技术主线。

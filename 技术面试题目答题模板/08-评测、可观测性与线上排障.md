# 08 · 评测、可观测性与线上排障

> 核心问题：怎么证明 Agent 做得好、为什么坏、坏了怎么快速恢复。

## 1. 为什么 Agent 的评测比传统软件难？

```commandline
有四个原因。

第一，非确定性。同样的输入，模型可能给出不同输出；温度、模型版本、上下文顺序都会影响结果。传统测试的「断言相等」不适用。

第二，多步链路。一个任务可能经过意图识别、检索、规划、工具调用、生成多个环节，最终错了不代表每一步都错，需要定位到具体环节。

第三，评价标准主观。什么算「好的测试用例」「准确的诊断」，往往需要业务专家判断，很难完全自动化。

第四，成本高。跑一次评测要消耗模型调用和工具资源，大规模评测既慢又贵。

所以 Agent 评测不能只做「最终答案对不对」，还要看过程：工具选对没有、步骤是否可执行、证据是否充分、人工改了多少。过程指标往往比最终分数更有诊断价值。
```

## 2. 评测集应该怎么建？

```commandline
我会按「真实、分层、可维护」三个原则建。

真实：样本来自真实业务需求和历史缺陷，而不是自己编的简单题。至少覆盖典型场景、边界情况、失败案例和不可回答问题。

分层：按任务类型、难度、风险等级分组。比如简单问答、复杂规划、工具调用、长任务、安全对抗。每组单独看指标，不能只用一个总分。

标注：每条样本要有输入、期望输出或验收标准、应召回的文档、允许的工具、评分规则。主观题要有评分细则，减少标注者差异。

防泄漏：评测集不能出现在训练数据或 Prompt 示例里；定期检查模型是否「见过」这些题。

可维护：线上失败案例定期补充，过时样本清理，版本化管理。评测集本身也是资产，不是一次性文件。
```

## 3. Agent 应该看哪些指标？

```commandline
我会分四层。

结果层：任务成功率、端到端完成率、人工修改率、转人工率、用户采纳率。

过程层：意图识别准确率、路由准确率、检索召回率、工具选择正确率、参数正确率、步骤可执行率、关键测试点覆盖率。

质量层：答案正确性、引用准确率、幻觉率、拒答准确率、格式合规率。

工程层：P50/P95 延迟、TTFT、单任务 Token 成本、重试率、失败恢复率。

不同任务用不同指标组合。比如测试用例生成更看「关键测试点覆盖率」和「人工修改率」，排障 Agent 更看「根因命中率」和「证据充分性」。

指标要能按版本、场景、租户下钻，否则只是一个好看的总数。
```

## 4. 离线评测和在线评测怎么配合？

```commandline
离线评测用于快速迭代和回归：每次改 Prompt、换模型、调检索都跑一遍，成本可控、可重复。它适合发现明显退化和比较方案。

在线评测用于验证真实价值：灰度发布、A/B 测试，看使用率、人工修改率、转人工率、任务完成时间。线上数据更真实，但噪声大、周期长。

两者要能对上。离线指标提升但线上没变化，可能是评测集失真；线上变差但离线没发现，说明评测集缺样本。

我的做法是：离线做门禁，线上做验证。离线不达标的版本不上线；线上出现异常能回滚，并把失败样本补进离线集。

不要只用离线分数做决策，也不要在没有离线回归的情况下直接全量上线。
```

## 5. Agent 失败了，怎么做归因？

```commandline
我会沿着执行链路分层排查：需求理解 → 检索 → 规划 → 工具选择 → 参数 → 执行环境 → 结果校验 → 生成。

每一步都有输入输出和状态，先找到「第一处分叉点」：从哪一步开始，结果和预期不一致。后面的错误往往是前面错误的放大。

常见归因：
- 理解错：意图识别或澄清不够；
- 检索错：召回不到或召回了错误文档；
- 规划错：步骤缺失、顺序错、依赖没闭合；
- 工具错：选错工具、参数错、权限不足；
- 环境错：超时、限流、依赖不可用；
- 校验错：没有发现错误结果。

归因不能只看最终答案，要看轨迹。最好有自动归因器，按规则和模型辅助分类，再由人工抽检校准。

归因的结果要能指导优化：不同原因对应不同修复手段，不能都归结为「模型不行」。
```

## 6. Agent 的可观测性应该怎么做？

```commandline
三件套：日志、指标、追踪。

日志要结构化，至少包含 trace ID、任务 ID、步骤、模型、Prompt 版本、工具、参数摘要、结果状态、耗时、错误码。不要打印完整敏感内容。

指标分系统指标和业务指标：QPS、延迟、错误率、Token、成本；任务成功率、人工修改率、转人工率。

追踪要把一次任务的所有步骤串起来：模型调用、检索、工具执行、审批、重试。每个 span 记录输入输出摘要和耗时，能看到瓶颈在哪。

Agent 还要额外记录「决策依据」：为什么选这个工具、为什么走这条路由、检索到了哪些文档。这些是普通 APM 没有的。

可观测性不是上线后才补，设计时就要埋点。否则出了问题只能靠猜。
```

## 7. 排障 Agent 怎么设计？

```commandline
我会把它设计成一个独立的子系统，而不是给聊天机器人加几个查询工具。

第一步，统一故障输入：告警、日志、指标、变更记录、执行轨迹，整理成结构化的故障上下文。

第二步，故障分类：按症状和影响面做分层分类，先判断是哪一类问题，缩小范围。

第三步，证据驱动的根因假设：不要只生成一个根因，而是生成多个假设，每个假设对应可验证的检查动作；用信息增益选择下一步查什么。

第四步，动态诊断 Workflow：根据证据决定下一步，而不是固定脚本；LLM 可以提议，但 Workflow 要经过校验。

第五步，受控恢复：恢复动作按风险分级，低风险自动执行，高风险审批；执行前有验证门，执行后有回滚方案。

第六步，经验沉淀：把确认过的故障案例结构化保存，下次复用，但必须验证适用边界。

排障 Agent 的价值不是「替人查」，而是「把专家的排查路径变成可复用、可验证的流程」。
```

## 8. 线上事故怎么处理？

```commandline
按「止损—同步—定位—修复—复盘」推进。

止损优先：回滚、降级、切人工、限流，先让业务恢复，不要一边查一边扩大影响。

同步要透明：影响范围、当前处置、下一次更新时间，不猜测原因，不隐瞒。对外统一口径。

定位靠证据：看指标、日志、追踪、变更记录，找到第一处分叉点。不要先入为主地认为是模型问题。

修复要分短期和长期：短期先恢复，长期补机制，比如监控、熔断、幂等、审批。

复盘对事不对人：还原时间线，区分直接原因和机制原因，明确改进项、责任人和时间。重点问「为什么没提前发现」「为什么没兜住」，而不是找一个人背锅。

最后把这次 case 补进评测集和演练场景，确保同类问题能被提前发现。
```

## 9. 如何做回归和防劣化？

```commandline
核心是「版本化 + 自动化 + 门禁」。

版本化：Prompt、模型、Agent 配置、工具、知识库都要有版本，每次评测记录完整的版本指纹。否则不知道效果变化是哪一项引起的。

自动化：每次提交或发布前跑评测集，覆盖核心场景和历史失败案例。能自动判分的自动判分，不能的做人工抽检。

门禁：设定阈值，关键指标低于阈值就不允许发布；允许个别指标波动，但不能整体退化。

灰度：新版本先小流量，观察在线指标，再逐步放量；保留一键回滚。

防劣化还要关注「隐性退化」：某些场景成功率没变，但人工修改率上升、延迟变高、成本变大。所以指标要多维，不能只看一个。

回归不是一次性的测试，而是持续的过程。
```

## 10. 模型输出不稳定（flaky）怎么处理？

```commandline
先区分「真随机」和「环境不稳定」。

真随机来自采样和模型本身。处理方式：关键任务降低温度；多次运行取一致性最高的结果；用规则或 Schema 校验兜底；对必须确定的场景改用确定性流程。

环境不稳定来自上下文顺序、并发、缓存、上游降级、工具超时。处理方式：固定输入和上下文顺序；隔离缓存；记录每次运行的版本和环境；对上游做重试和熔断。

评测时不能只跑一次。对 flaky 场景要跑多次，看通过率和方差，而不是看单次结果。

如果某个用例长期不稳定，要判断是「模型能力边界」还是「测试本身不确定」。前者调整预期或加人工，后者修测试。

不要用「多跑几次取最好」来掩盖真实的不稳定。
```

## 11. 怎么衡量一个 Agent 项目值不值得做？

```commandline
我会看三层价值。

第一层，效率：单个任务节省多少时间、减少多少重复劳动、人工修改率多少。这是最直接的。

第二层，质量：有没有减少遗漏、降低错误率、提前发现问题。比如测试 Agent 有没有帮助发现原本会漏掉的测试点。

第三层，业务：使用率、留存、采纳率、对交付周期的影响。没有进入工作流的功能，技术指标再好也没有价值。

成本侧要算：模型调用、工具资源、人力维护、评测和排障成本。有些场景看起来省了时间，但维护成本更高。

我的判断是：先在一个高频、规则相对明确、结果可验证的场景做深，用真实数据证明价值，再扩展。不要一开始就追求全流程自动化。
```

## 12. 设计一个 Agent 评测系统，核心模块有哪些？

```commandline
我会分成六个模块。

第一，数据集管理：样本、标注、分组、版本、防泄漏。

第二，执行引擎：按配置跑 Agent，支持并发、重试、超时、mock 工具和模型，保证可重复。

第三，评分器：规则评分、模型评分、人工评分，支持多指标和加权。

第四，归因分析：按轨迹定位失败环节，输出分类统计和典型案例。

第五，实验管理：记录版本指纹（Prompt、模型、配置、工具、知识库），支持 A/B 和对比。

第六，门禁与报表：CI 集成、阈值判断、趋势看板、失败样本回流。

关键设计是「版本指纹」和「轨迹记录」。没有它们，评测结果无法复现，也无法解释变化来自哪里。

评测系统本身也要控制成本：分层抽样、缓存、mock、按需跑全量。
```
